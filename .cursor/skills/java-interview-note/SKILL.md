# Java Interview Note

Превращает исходный конспект вопросов/ответов в полноценную учебную заметку для
senior-подготовки — в стиле:
`src/main/java/ru/stas/pupkov/preparations/oop/oop.md`.
`src/main/java/ru/stas/pupkov/preparations/jvm/jvm.md`.

Соблюдай также workspace-правило Java/Spring Tutor (пути разделов, `code/`, md только
после разрешения пользователя).

## Когда применять

Пользователь просит обработать тему/файл из interview-репозитория или сделать заметку. 
Типичные источники: `https://github.com/enhorse/java-interview` (`*.md` в корне).

## Workflow

1. **Прочитать источник целиком** (raw GitHub / локальная копия). Не опираться только на TOC.
2. **Кратко разобрать в чате** (покрытие, пробелы, неточности), если пользователь ещё не дал
   добро на создание md — или сразу писать заметку, если явно попросил создать/обновить.
3. **Согласовать имя раздела** (kebab-case), если раздела ещё нет:
   `oop`, `java-core`, `concurrency`, `jvm`, `jcf`, `databases`, …
4. **Создать/обновить**:
   - заметку: `src/main/java/ru/stas/pupkov/preparations/<раздел>/<тема>.md`
   - демо: `.../<раздел>/code/*Demo.java` (runnable, `main`, один public top-level класс)
5. **Скомпилировать и прогнать демо** (`./gradlew -q compileJava` + `java -cp ...`), но
   **не вставлять** блок команд запуска в заметку.
6. В конце чата — коротко что создано (пути). Не дублировать всю заметку в ответе.

## Цель заметки

Готовый документ для изучения темы: полное и понятное изложение, примеры, нюансы уровня
senior/staff. Не рецензия на исходник и не «конспект правок».

### Обязательно

- Исправить ошибки и спорные утверждения источника; дополнить пробелы (JVM/JLS, trade-offs,
  production-практика, современные Java 17+ где уместно).
- Раскрывать темы с пояснениями и примерами кода в тексте (не сухой список определений).
- Структура: заголовок, краткий контекст (версия Java и т.п.), содержание со ссылками,
  тематические разделы, блок демо со ссылками, блок «Вопросы для собеседования и ответы».
- В Q&A — развёрнутые ответы. Без мета-блоков вроде «на что смотрит интервьюер».
- Ссылки на демо: относительные markdown-пути, например `[BindingDemo.java](code/BindingDemo.java)`.

### Запрещено в заметке

- Мета про исходный файл: «в исходнике ошибка», «корректировка для собеса», «спорная
  академическая позиция», «учебник пишет иначе».
- Лирические отступления и вода.
- Блок `./gradlew` / `java -cp ...` для запуска демо.
- Junior-trivia без практической ценности; разжёвывание азбуки без запроса.

## Стиль и терминология

- Язык заметки — **русский**.
- Уровень — **senior**: нюансы, контракты, механика, антипаттерны; без «очевидных» вводных.
- Принятые англицизмы оставлять. Формат первого упоминания — **сначала русский**,
  затем английский в скобках:

  `Принцип подстановки Барбары Лисков (Liskov Substitution Principle, LSP)`

  Дальше по заметке — только англицизм (`LSP`, `DI`, `override` …) без повторного перевода.
  То же для getter/setter, God-object, overload, runtime/compile-time, fragile base class,
  Template Method, sealed, DTO, use-case и т.п.
- Ключевые слова и API Java не переводить (`interface`, `extends`, `invokevirtual`).
- Имена демо-классов и пакетов — на английском.

## Содержание по качеству

Ориентир глубины — эталон `oop.md`:

| Элемент | Ожидание |
|--------|----------|
| Определения | точные, рабочие, без догм |
| Пояснения | зачем, когда применять, типичные ловушки |
| Примеры | короткие фрагменты в md + полные runnable в `code/` |
| Сравнения | таблицы trade-offs где уместно |
| Актуальность | Java 17+ (toolchain проекта), устаревшее помечать явно |
| Q&A | 8–15 вопросов senior-уровня с полными ответами |

Не копировать метафоры источника буквально, если они раздувают текст без пользы; можно
кратко иллюстрировать, но приоритет — код и контракты.

## Демо-код

- Package: `ru.stas.pupkov.preparations.<раздел>.code`
- Самодостаточный файл с `main`, понятный вывод в консоль
- Покрывать ключевые ловушки темы (не «Hello World»)
- В заметке — таблица «файл → что показывает»
- Не трогать остальные файлы проекта без просьбы
