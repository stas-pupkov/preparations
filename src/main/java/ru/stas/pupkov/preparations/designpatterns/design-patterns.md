## 1. Что такое паттерн

Паттерн — **типовое решение типовой проблемы проектирования**, не копируемый сниппет.  
Алгоритм = рецепт шагов; паттерн = чертёж решения (реализация в двух проектах может отличаться).

Обычная структура описания: проблема → мотивация → структура классов → код → применимость → связи.

### Порождающие (5)

#### Factory Method

**Суть.** Интерфейс создания продукта в суперклассе; конкретный тип определяют подклассы.

**Проблема.** Клиентский код жёстко завязан на `new ConcreteProduct`. Добавление нового вида продукта (другой транспорт, другой UI-виджет) размазывает `if/switch` по всей программе и ломает OCP.

**Решение.** Создание выносится в фабричный метод. Базовый код работает с продуктом через общий интерфейс; подкласс переопределяет метод и подставляет нужный тип. `new` никуда не делся — он живёт внутри фабрики, а не в бизнес-логике клиента.

Java / Spring: `FactoryBean`. Демо: [FactoryMethodDemo.java](code/FactoryMethodDemo.java).

#### Abstract Factory

**Суть.** Создание семейств связанных продуктов без привязки к конкретным классам.

**Проблема.** Нужны согласованные наборы объектов (кнопка+чекбокс одной ОС, кресло+стол одного стиля). Создание «вразброс» даёт несочетаемые комбинации и привязывает клиент к куче конкретных классов.

**Решение.** Абстрактная фабрика объявляет методы создания всех типов семейства. Конкретная фабрика выпускает только одну вариацию. Клиент получает продукты через интерфейсы фабрики и продуктов; выбор семейства — на старте (конфиг, профиль).

Java / Spring: `@Profile` / конфиг выбирает фабрику. Демо: [AbstractFactoryDemo.java](code/AbstractFactoryDemo.java).

#### Builder

**Суть.** Пошаговая сборка сложного объекта; один процесс строительства — разные представления.

**Проблема.** Объект с десятками optional-полей: либо телескопические конструкторы, либо комбинаторный взрыв подклассов под каждую конфигурацию. Вызовы выглядят монструозно, часть параметров почти всегда `null`.

**Решение.** Конструирование выносится в Builder: шаги (`buildWalls`, `header`, …) вызываются по необходимости. Director (опционально) задаёт порядок для типовых сценариев. Продукт отдаётся только после `build()`.

Java / Spring: `UriComponentsBuilder`, `WebClient.builder()`. Демо: [BuilderDemo.java](code/BuilderDemo.java).

#### Prototype

**Суть.** Копирование объектов через общий контракт, без знания конкретного класса.

**Проблема.** Скопировать объект «снаружи» нельзя: часть состояния private, а привязка копирующего кода к классам ломает работу через интерфейсы. Плодить подклассы «только ради разных стартовых конфигураций» тоже дорого.

**Решение.** Объект сам умеет себя клонировать (`copy` / copy-ctor). Клиент просит копию у интерфейса прототипа. Опционально — реестр заранее настроенных прототипов вместо иерархии конфигурационных подклассов.

Java / Spring: copy-ctor; `@Scope("prototype")` — новый бин из определения, не GoF-клон состояния. Демо: [PrototypeDemo.java](code/PrototypeDemo.java).

#### Singleton

**Суть.** Гарантия одного экземпляра класса и глобальная точка доступа к нему.

**Проблема.** Нужен общий ресурс (конфиг, соединение), и обычный конструктор каждый раз создаёт новый объект. Глобальная переменная не защищена от подмены.

**Решение.** Скрыть конструктор, отдать доступ через `getInstance` / enum-constant, контролировать жизненный цикл в одном месте. Цена: скрытые зависимости, проблемы с тестами и многопоточностью при наивной реализации.

Java / Spring: enum-singleton; контейнерный singleton ≠ GoF. Демо: [SingletonDemo.java](code/SingletonDemo.java).

### Структурные (7)

#### Adapter

**Суть.** Объект-переводчик: несовместимые интерфейсы работают вместе.

**Проблема.** Есть полезный сервис (библиотека, legacy), но его API не совпадает с тем, что ждёт клиент. Переписывать сервис нельзя или слишком дорого.

**Решение.** Адаптер реализует интерфейс клиента и делегирует в сервис, преобразуя вызовы/данные. Клиент зависит только от своего контракта; смена версии сервиса локализуется в адаптере.

Java / Spring: `HandlerAdapter`, `InputStreamReader`. Демо: [AdapterDemo.java](code/AdapterDemo.java).

#### Bridge

**Суть.** Разделение абстракции и реализации на две иерархии, связанные композицией.

**Проблема.** Класс нужно расширять в двух независимых плоскостях (фигура×цвет, GUI×платформа). Наследование даёт комбинаторный взрыв подклассов.

**Решение.** Одна ось остаётся «абстракцией» (управляющий слой), вторая выносится в отдельную иерархию реализаций. Абстракция держит ссылку на реализацию и делегирует. Оси меняются независимо.

Java / Spring: `PlatformTransactionManager` × реализации. Демо: [BridgeDemo.java](code/BridgeDemo.java).

#### Composite

**Суть.** Дерево объектов; лист и контейнер имеют общий интерфейс.

**Проблема.** Модель естественно древовидная (заказ из коробок и товаров, UI-меню). Клиенту приходится различать «простое» и «составное» и писать рекурсивный обход вручную в каждом месте.

**Решение.** Общий компонент: у листа операция локальна, у контейнера — делегирование детям и агрегация результата. Клиент вызывает один метод на корне, не зная структуры.

Java / Spring: role hierarchy, UI trees. Демо: [CompositeDemo.java](code/CompositeDemo.java).

#### Decorator

**Суть.** Динамически добавить поведение, оборачивая объект в совместимые обёртки.

**Проблема.** Нужны комбинации доп. фич (email+SMS+Slack). Подклассы на каждую комбинацию взрывают иерархию.

**Решение.** Базовый объект + декораторы с тем же (или расширенным) интерфейсом. Обёртки можно стекать в runtime. Отличие от Proxy: обычно не владеют lifecycle сервиса, а наращивают поведение «снаружи».

Java / Spring: I/O streams, `BeanPostProcessor`. Демо: [DecoratorDemo.java](code/DecoratorDemo.java).

#### Facade

**Суть.** Упрощённый интерфейс к сложной подсистеме.

**Проблема.** Бизнес-код вынужден знать порядок инициализации и десятки классов библиотеки/фреймворка. Логика клиента склеивается с деталями подсистемы.

**Решение.** Фасад даёт узкий API «под задачу клиента» и сам оркестрирует подсистему. Полный функционал может быть недоступен — это осознанный trade-off. Риск: фасад превращается в god-object.

Java / Spring: `JdbcTemplate`. Демо: [FacadeDemo.java](code/FacadeDemo.java).

#### Flyweight

**Суть.** Экономия памяти: общее (intrinsic) состояние разделяется, уникальное (extrinsic) передаётся снаружи.

**Проблема.** Очень много похожих объектов; повторяющиеся тяжёлые поля (текстура, стиль) дублируются в каждом экземпляре и съедают RAM.

**Решение.** Вынести повторяющееся immutable-состояние в легковесы, кешировать их фабрикой. Контекст (координаты и т.п.) хранить отдельно и передавать в методы. Имеет смысл только при реальном давлении на память.

Java / Spring: кэши, идея String/`Integer` pool. Демо: [FlyweightDemo.java](code/FlyweightDemo.java).

#### Proxy

**Суть.** Заменитель с тем же интерфейсом; до/после вызова — доп. логика, затем делегирование.

**Проблема.** Нужен контроль доступа к сервису: lazy-init, кеш, security, remote, логирование. Вшивать это в сам сервис или дублировать в каждом клиенте нельзя/неудобно.

**Решение.** Proxy реализует тот же интерфейс, что сервис. Клиент не отличает proxy от оригинала. Часто proxy сам создаёт/держит lifecycle сервиса (в отличие от Decorator).

Java / Spring: JDK/CGLIB, AOP, `@Transactional`. Демо: [ProxyDemo.java](code/ProxyDemo.java).

### Поведенческие (10)

#### Chain of Responsibility

**Суть.** Запрос идёт по цепочке обработчиков; каждый решает — обработать и/или передать дальше.

**Проблема.** Запрос проходит серию проверок/обработок (auth → roles → throttle). Жёсткая связка «отправитель знает всех получателей» и раздутый `if` в одном месте плохо расширяются.

**Решение.** Обработчики связываются в цепь с общим контрактом. Отправитель шлёт запрос первому; порядок и состав цепи настраиваются без правки клиента. Аналог в инфре — middleware / filter pipeline.

Java / Spring: Filter / Security chain. Демо: [ChainOfResponsibilityDemo.java](code/ChainOfResponsibilityDemo.java).

#### Command

**Суть.** Запрос превращается в объект: его можно ставить в очередь, логировать, отменять.

**Проблема.** Нужны отложенный запуск, undo/redo, макросы, единый способ передать «действие» в UI/воркер. Прямой вызов метода не сохраняет параметры и историю.

**Решение.** Команда инкапсулирует получателя + параметры операции. Invoker работает с командами одинаково; история хранит команды для undo. Отличие от Strategy: упаковка действия, а не выбор способа одного действия.

Java / Spring: events / job objects. Демо: [CommandDemo.java](code/CommandDemo.java).

#### Iterator

**Суть.** Последовательный обход элементов без раскрытия внутренней структуры коллекции.

**Проблема.** Коллекция сложная (дерево, граф, remote API). Алгоритмы обхода раздувают класс хранения; клиенту нельзя светить internals; нужны разные способы обхода одной структуры.

**Решение.** Отдельный итератор держит курсор обхода. Коллекция отдаёт итератор через фабричный метод. Клиент знает только `hasNext`/`next` (или аналог).

Java / Spring: `Iterator`, Spring Data `Page`. Демо: [IteratorDemo.java](code/IteratorDemo.java).

#### Mediator

**Суть.** Компоненты общаются через посредника, а не напрямую друг с другом.

**Проблема.** N виджетов/сервисов знают друг о друге → плотный граф связей, любая правка UI/потока трогает много классов.

**Решение.** Mediator централизует взаимодействие: компоненты шлют события посреднику, он решает, кого уведомить. Снижается coupling между коллегами; риск — раздутый mediator. Отличие от Facade: коллеги знают о посреднике и координируются через него.

Java / Spring: `ApplicationEventPublisher` как шина. Демо: [MediatorDemo.java](code/MediatorDemo.java).

#### Memento

**Суть.** Сохранить и восстановить прошлое состояние, не раскрывая internals объекта.

**Проблема.** Нужен undo/snapshot. Если caretaker лезет в поля originator — ломается инкапсуляция; если originator отдаёт всё публично — тоже.

**Решение.** Originator сам создаёт снимок (memento) со своим состоянием. Caretaker хранит снимки как opaque-объекты и возвращает их originator'у для restore. Снаружи снимок не читают и не правят.

Java / Spring: UI undo; в ядре Spring нет прямого аналога. Демо: [MementoDemo.java](code/MementoDemo.java).

#### Observer

**Суть.** Механизм подписки: наблюдатели реагируют на события издателя.

**Проблема.** Объект A должен реагировать на изменения B, но B не должен знать всех заинтересованных (иначе жёсткая связь и опрос в цикле).

**Решение.** Издатель хранит список подписчиков и уведомляет их при событии. Подписка/отписка динамические. В Spring — внутрипроцессный pub/sub через события контекста.

Java / Spring: `@EventListener`. Демо: [ObserverDemo.java](code/ObserverDemo.java).

#### State

**Суть.** Поведение объекта меняется вместе с внутренним состоянием (выглядит как смена класса).

**Проблема.** Конечный автомат размазан по гигантским `switch(status)` в каждом методе. Добавление статуса трогает все методы; переходы неявны.

**Решение.** Каждое состояние — отдельный объект с методами реакций. Контекст делегирует текущему состоянию; переходы часто инициирует само состояние. Отличие от Strategy: состояния знают о переходах и связаны жизненным циклом объекта.

Java / Spring: статусы заказа / Statemachine. Демо: [StateDemo.java](code/StateDemo.java).

#### Strategy

**Суть.** Семейство взаимозаменяемых алгоритмов; выбор в runtime через композицию.

**Проблема.** Несколько вариаций одного действия (маршрут, оплата) раздувают класс условиями. Правка одной вариации рискует сломать остальные.

**Решение.** Общий интерфейс стратегии + конкретные классы. Контекст держит ссылку и делегирует. Клиент/конфиг подставляет нужную стратегию. Стратегии обычно не переключают друг друга (в отличие от State).

Java / Spring: несколько `@Bean` одного интерфейса. Демо: [StrategyDemo.java](code/StrategyDemo.java).

#### Template Method

**Суть.** Скелет алгоритма в базовом классе; отдельные шаги переопределяют подклассы.

**Проблема.** Несколько классов делают почти один pipeline, отличаясь деталями шагов. Дублирование каркаса; правка общего порядка копируется вручную.

**Решение.** Шаблонный метод фиксирует порядок вызовов шагов. Шаги — abstract, default или hooks. Подклассы меняют шаги, не трогая структуру. Альтернатива без наследования — Strategy / callbacks (`JdbcTemplate`).

Java / Spring: `JdbcTemplate` + callbacks. Демо: [TemplateMethodDemo.java](code/TemplateMethodDemo.java).

#### Visitor

**Суть.** Новая операция над иерархией элементов без изменения их классов (double dispatch).

**Проблема.** Нужны новые поведения над стабильной иерархией (export XML/JSON), но править классы элементов нельзя или нежелательно (чужеродная ответственность).

**Решение.** Операция живёт в Visitor (`visitConcreteA/B`). Элементы принимают visitor через `accept` и вызывают нужный `visit*` (вторая диспетчеризация). Новый тип элемента дорог: правка всех visitor. Выгоден, когда типы редки, а операции часты.

Java / Spring: `FileVisitor`. Демо: [VisitorDemo.java](code/VisitorDemo.java).

## 4. Часто путают

| A | B | Различие |
|---|---|----------|
| Adapter | Facade | Adapter стыкует существующие интерфейсы; Facade даёт новый упрощённый API |
| Adapter | Proxy | Proxy — тот же интерфейс; Adapter — другой |
| Decorator | Proxy | Decorator наращивает поведение; Proxy часто владеет lifecycle |
| Decorator | Composite | Decorator — одна обёртка; Composite — много детей |
| Bridge | Strategy | Одинаковая композиция; Bridge — структура двух осей; Strategy — смена алгоритма |
| State | Strategy | В State состояния сами переключают контекст |
| Command | Strategy | Command упаковывает действие; Strategy — разные способы одного действия |
| Template Method | Strategy | Наследование vs делегирование |
| Mediator | Facade | Facade не координирует «все со всеми»; Mediator централизует общение |
| Abstract Factory | Builder | Factory сразу отдаёт продукт семейства; Builder — пошагово |
| Factory Method | Abstract Factory | FM — один продукт; AF — семейство |
| Singleton | Flyweight | Flyweight: много immutable shared; Singleton: один + global access |
| GoF Singleton | Spring singleton | Контейнерный scope на ApplicationContext, не static getInstance |

## 7. Вопросы для собеседования и ответы

### 1. Чем паттерн отличается от алгоритма и от архитектурного стиля?

Алгоритм задаёт шаги достижения цели. Паттерн — высокоуровневый чертёж решения проблемы дизайна (структура классов/связей). Архитектурный стиль (layered, hexagonal) задаёт организацию **всей** системы; GoF-паттерны — локальные решения внутри неё.

### 2. Почему Spring bean «singleton» ≠ GoF Singleton?

GoF: скрытый конструктор + глобальная точка доступа (`getInstance`). Spring: один экземпляр **на контейнер**, создаётся и внедряется DI; тестируемость и сменность scope сохраняются. Это контейнерный lifecycle, не паттерн «глобальной переменной».

Демо: [SingletonDemo.java](code/SingletonDemo.java).

### 3. Adapter vs Facade vs Proxy — по одному примеру

- Adapter: XML-клиент → JSON-библиотека ([AdapterDemo.java](code/AdapterDemo.java)).
- Facade: `JdbcTemplate` вместо ручного JDBC ([FacadeDemo.java](code/FacadeDemo.java)).
- Proxy: caching/AOP proxy с тем же интерфейсом ([ProxyDemo.java](code/ProxyDemo.java)).

### 4. Когда Strategy лучше Template Method и наоборот?

Strategy — когда алгоритм меняется **в runtime** и варианты независимы (платёжный канал).  
Template Method — когда **скелет** фиксирован, варьируются шаги, и наследование уместно (парсеры форматов, `JdbcTemplate`).

Демо: [StrategyDemo.java](code/StrategyDemo.java), [TemplateMethodDemo.java](code/TemplateMethodDemo.java).

### 5. State vs Strategy: кто инициирует смену поведения?

В Strategy контекст/клиент подставляет стратегию; стратегии обычно не знают друг о друге.  
В State переходы часто живут **внутри** состояний (`state.publish(ctx)` → `ctx.changeState(...)`).

Демо: [StateDemo.java](code/StateDemo.java).

### 6. Почему Visitor бьёт OCP по операциям, но ломает при новых типах?

Новая операция = новый Visitor, элементы не трогаем. Новый тип элемента = правка **всех** Visitor и интерфейса. Выгоден при стабильной иерархии и частых новых операциях.

Демо: [VisitorDemo.java](code/VisitorDemo.java).

### 7. Где Decorator уже в JDK I/O?

`FilterInputStream` / `BufferedInputStream` / `DataInputStream` — цепочки обёрток с общим `InputStream`.  
В Spring — обёртка бина через `BeanPostProcessor` / AOP.

Демо: [DecoratorDemo.java](code/DecoratorDemo.java).

### 8. Abstract Factory vs DI-контейнер

AF — явный паттерн семейств продуктов. DI-контейнер часто **заменяет** ручные фабрики: выбор реализации через конфиг/`@Profile`. Паттерн остаётся там, где важна гарантия согласованности семейства в коде фабрики.

Демо: [AbstractFactoryDemo.java](code/AbstractFactoryDemo.java).

### 9. Когда оправдан Flyweight?

Много объектов, память упирается, большая часть состояния повторяется и может быть immutable shared. Иначе — лишняя сложность; нормальный кэш/нормализация данных проще.

Демо: [FlyweightDemo.java](code/FlyweightDemo.java).

### 10. Chain of Responsibility vs middleware pipeline

Это один intent: последовательные обработчики с возможностью остановить/продолжить. Servlet Filter, Spring Security filter chain, Netty/WebFlux handlers — промышленные формы CoR.

Демо: [ChainOfResponsibilityDemo.java](code/ChainOfResponsibilityDemo.java).
