## 1. База данных и СУБД

**База данных (database)** — организованный набор данных, приспособленный к хранению
и обработке вычислительной системой. Организация подразумевает схему, ограничения
целостности и операции выборки/изменения.

**СУБД (Database Management System, DBMS)** — ПО, которое:

- хранит данные и метаданные схемы;
- обеспечивает язык определения и манипулирования данными (DDL / DML; в SQL — единый язык);
- поддерживает конкурентный доступ, транзакции, журналирование;
- отвечает за резервное копирование, восстановление, безопасность, оптимизацию запросов.

Для backend-разработчика важно разделять:

| Слой | Примеры |
|------|---------|
| Логическая модель | отношения, ключи, нормальные формы |
| Физическая модель | страницы/heap, индексы, vacuum, WAL |
| Доступ из приложения | JDBC, connection pool, ORM, isolation level |

«База» в разговоре часто означает и данные, и конкретный инстанс PostgreSQL/MySQL —
на собесе лучше уточнять, о чём речь.

## 2. Реляционная модель

Реляционная модель данных (relational model) — логическая модель Кодда:

1. **Структура** — данные как отношения (relation ≈ таблица): множество кортежей
   (tuple ≈ строка) над доменами атрибутов (attribute ≈ столбец).
2. **Целостность** — ограничения домена, сущности (ключи), ссылочная целостность
   (foreign key).
3. **Манипулирование** — реляционная алгебра / исчисление; в практике — SQL
   (декларативное описание результата, план строит оптимизатор).

Важные уточнения для собеса:

- «Таблица» в SQL — реализация отношения с нюансами: допускает дубликаты без ключа,
  порядок строк не определён, `NULL` — трёхзначная логика.
- Реляционная алгебра оперирует множествами; SQL ближе к мультимножествам (bag),
  пока не сказали `DISTINCT` / есть ключ.
- Нормальные формы — свойства **схемы отношения** относительно функциональных
  (и иных) зависимостей, а не «магическая кнопка производительности».

## 3. Ключи

### Виды ключей

| Термин | Смысл |
|--------|--------|
| Простой ключ | один атрибут |
| Составной ключ (composite key) | два и более атрибута |
| Потенциальный ключ (candidate key) | минимальный набор атрибутов, уникально идентифицирующий кортеж |
| Первичный ключ (primary key) | выбранный candidate key «по умолчанию» |
| Альтернативный ключ (alternate key) | остальные candidate keys (часто `UNIQUE`) |
| Внешний ключ (foreign key) | набор атрибутов, значения которых должны совпадать с candidate key другого (или того же) отношения |
| Суррогатный ключ (surrogate key) | искусственный идентификатор (`BIGSERIAL`, UUID), не из предметной области |
| Естественный ключ (natural key) | из домена (ИНН, email), если стабилен и уникален |

**Минимальность** candidate key: нельзя убрать атрибут, не потеряв уникальность.
Набор `{passport, name}` при уникальном `passport` — не candidate key (избыточен).

### Выбор primary key

Практические критерии:

- стабильность во времени (не «номер телефона, который меняют»);
- компактность для FK и индексов (`bigint` часто выгоднее широкого natural key);
- отсутствие смысловой нагрузки, которую потом «поправят» бизнесом.

В OLTP почти всегда суррогат + `UNIQUE` на естественные идентификаторы.
Natural PK уместен, когда значение действительно неизменно и узкое (код валюты ISO).

### Foreign key

FK обеспечивает ссылочную целостность (referential integrity): нельзя сослаться
на несуществующую строку; поведение при удалении/обновлении родителя задаётся
`ON DELETE` / `ON UPDATE` (`RESTRICT`/`NO ACTION`, `CASCADE`, `SET NULL`, `SET DEFAULT`).

В приложении на Hibernate «есть `@ManyToOne`» ≠ «в БД есть FK». На проде FK — защита
от грязных данных и гонок записи; отказ от FK ради скорости — осознанный trade-off
(часто в шардированных/event-sourcing схемах).

## 4. Связи

Кардинальность на уровне предметной области:

| Связь | Смысл | Типичная реализация |
|-------|--------|---------------------|
| 1:1 | каждой A соответствует не более одной B и наоборот | FK в одной из таблиц + `UNIQUE` на FK; иногда общая PK |
| 1:N | у A много B; у B один A | FK в «многих» |
| M:N | обе стороны ко многим | связующая таблица (associative / join table) с PK/UNIQUE по паре FK |

Примеры:

- 1:1 — `User` ↔ `UserProfile` (профиль не существует без пользователя);
- 1:N — `University` → `Faculty`;
- M:N — `Professor` ↔ `Faculty` через `faculty_professor(faculty_id, professor_id)`.

Связь «многие-ко-многим» **не** хранят двумя FK «друг на друга» в родительских
таблицах — только через отношение связи (иногда с собственными атрибутами:
`enrolled_at`, `role`).

Опциональность (0..1 vs 1) — отдельное измерение: nullable FK, отдельная таблица
1:1, исключающие ограничения.

## 5. Нормализация и денормализация

**Нормализация** — пошаговая декомпозиция схемы для устранения избыточности и
аномалий обновления/вставки/удаления. Цель — логическая непротиворечивость, а не
«меньше гигабайт на диске» и не автоматический выигрыш в latency.

### Нормальные формы (рабочий минимум + уточнения)

| Форма | Суть |
|-------|------|
| **1NF** | атрибуты атомарны; нет повторяющихся групп как вложенных таблиц в ячейке |
| **2NF** | 1NF + каждый неключевой атрибут полно зависит от **всего** candidate key (актуально для составных ключей) |
| **3NF** | 2NF + нет транзитивных зависимостей неключевых атрибутов от ключа (неключ → неключ → …) |
| **BCNF** | каждая детерминанта нетривиальной FD — candidate key (строже 3NF) |
| **4NF** | нет нетривиальных многозначных зависимостей (multivalued dependency), не определяемых ключом |
| **5NF** | каждая нетривиальная join dependency следует из candidate keys |
| **6NF** | неприводимость относительно join dependencies; чаще в темпоральных моделях |
| **DKNF** | все ограничения — следствия доменов и ключей (теоретический идеал) |

Формулировка «в 3NF неключевые атрибуты не зависят друг от друга» — бытовое упрощение.
Точнее: нет FD вида `неключ → неключ`, из-за которой неключ транзитивно зависит от ключа.

Пример нарушения 2NF (составной ключ `(order_id, product_id)`, атрибут `product_name`
зависит только от `product_id`) → вынести товары в отдельное отношение.

Пример нарушения 3NF: `employee(id, dept_id, dept_name)` — `dept_id → dept_name`
→ таблица `department`.

BCNF ловит случаи, когда часть составного ключа зависит от неключа
(классика: «преподаватель → предмет» при ключах вроде `(student, subject)`).

На практике OLTP-схемы целеустремлённо держат около **3NF/BCNF**; 4NF–6NF всплывают
реже и обычно в узких доменах.

### Денормализация

Осознанное введение избыточности ради:

- меньшего числа JOIN на горячем read-path;
- материализованных агрегатов / кэша в таблице;
- документо-ориентированного снимка для read-model (CQRS).

Цена: сложные обновления, корректность при гонках, рассинхрон реплик/кэша.
Денормализация без измерения узкого места — преждевременная оптимизация схемы.

## 6. Индексы

**Индекс (index)** — структура, ускоряющая поиск/соединение/сортировку и/или
обеспечивающая уникальность. Обычно хранит ключи + указатели на строки
(в кластерном индексе — сами строки в порядке ключа).

### Плюсы и минусы

| Плюсы | Минусы |
|-------|--------|
| Быстрый lookup / range / join | место на диске и в RAM (buffer pool / shared_buffers) |
| Поддержка `UNIQUE` / PK / FK (часто) | замедление `INSERT`/`UPDATE`/`DELETE` (поддержка индекса) |
| Covering index → index-only scan | риск деградации планов при устаревшей статистике |

### Кластерный vs некластерный

| | Кластерный (clustered) | Некластерный (secondary / non-clustered) |
|--|------------------------|------------------------------------------|
| Данные | строки физически (или логически в primary structure) упорядочены по ключу | отдельная структура со ссылками на heap / PK |
| Количество | обычно один на таблицу | много |
| Пример | InnoDB: таблица = B+tree по PK | InnoDB secondary index → PK; PostgreSQL: все индексы «вторичные» относительно heap |

В **PostgreSQL** нет постоянного clustered index как в InnoDB: `CLUSTER` — одноразовая
переукладка heap; дальше порядок плывёт. На собесе важно не смешивать термины
SQL Server/InnoDB с Postgres.

### Структуры, которые реально спрашивают

| Тип | Когда уместен |
|-----|----------------|
| **B-tree / B+tree** | равенство и диапазоны, сортировка, основной default |
| **Hash** | только равенство (в PG — ограниченные сценарии) |
| **Bitmap** | низкая кардинальность в аналитике (Oracle; в PG — bitmap scan по нескольким индексам на лету) |
| **GiST / GIN / BRIN** (PG) | гео/полнотекст/JSONB/очень большие append-only таблицы |
| **Partial index** | индекс по условию (`WHERE active`) |
| **Expression / function-based** | `lower(email)`, `(data->>'status')` |
| **Covering / INCLUDE** | ключ поиска + payload в листьях без похода в heap |
| **Full-text (inverted)** | поиск по словам |
| **Reverse key** | снятие hot spot на монотонном правом крае B-tree (чаще Oracle OLTP) |

Составной индекс: важен **порядок столбцов** (leftmost prefix).
Индекс `(a, b)` помогает по `a`, по `a,b`; обычно не по одному `b`.

### Селективность и seq scan

Низкая кардинальность (`boolean`, «пол») часто делает обычный B-tree бесполезным:
оптимизатор выбирает sequential scan. Исключения: partial index
(`WHERE deleted = false`), bitmap-подход в DW, комбинированный составной индекс,
где низкокардинальный столбец — не единственный.

Полное сканирование выгоднее индексного доступа, когда:

- читается большая доля таблицы (слабая селективность);
- данные плохо кластеризованы относительно индекса (много random I/O);
- таблица маленькая и целиком в кэше;
- многоблочное чтение дешевле цепочки «листья индекса + прыжки по heap».

Грубое правило: если объём **отфильтрованных** данных всё равно близок к полной
таблице, индекс только добавляет работу.

## 7. Транзакции и ACID

**Транзакция** — логическая единица работы, переводящая БД из одного согласованного
состояния в другое (commit) либо не меняющая видимого состояния (rollback).

**ACID:**

| Свойство | Смысл |
|----------|--------|
| **Atomicity** | все изменения транзакции применяются или ни одно |
| **Consistency** | после commit соблюдены объявленные ограничения целостности; инварианты приложения — ответственность кода + constraints |
| **Isolation** | параллельные транзакции не ломают оговорённые гарантии видимости |
| **Durability** | зафиксированное переживает краш (WAL + fsync / аналог) |

На практике «consistency» в ACID — про правила схемы, а не CAP-consistency.
Долговечность зависит от настроек (`fsync`, репликация, `synchronous_commit`).

В Java/Spring: граница транзакции — `Connection` / `@Transactional`; isolation и
propagation задают семантику, но не освобождают от корректной обработки
`OptimisticLockException` / deadlock retry.

Демо упрощённой модели commit/rollback: [TransactionAcidityDemo.java](code/TransactionAcidityDemo.java).

## 8. Аномалии параллельного доступа

| Аномалия | Суть |
|----------|------|
| **Lost update** | два обновления одной строки; итог одного затирается без учёта другого |
| **Dirty read** | прочитаны незакоммиченные данные, которые потом откатились |
| **Non-repeatable read** | повторный SELECT той же строки даёт другие значения (строку изменили/удалили) |
| **Phantom read** | повторный SELECT по предикату даёт другой **набор** строк (вставили/удалили подходящие) |
| **Write skew** (иногда отдельно) | каждая транзакция читает согласованный снимок и пишет «своё», вместе нарушая инвариант |

Фантом ≠ non-repeatable: во втором меняются уже прочитанные строки; в первом
меняется состав множества, подходящего под условие.

Lost update на уровне «два `UPDATE` подряд» часто лечат:

- `SELECT … FOR UPDATE` / пессимистической блокировкой;
- optimistic locking (`version` / `etag`);
- атомарным `UPDATE … SET balance = balance - 100 WHERE …`.

Демо иллюстрации аномалий (модель в памяти): [IsolationAnomaliesDemo.java](code/IsolationAnomaliesDemo.java).

## 9. Уровни изоляции

Поведение конкретной СУБД может отличаться от «учебной» картины — детали всегда
в документации движка. Пошаговые таймлайны:
[IsolationLevelsDetailedDemo.java](code/IsolationLevelsDetailedDemo.java).
Краткая матрица: [IsolationLevelsDemo.java](code/IsolationLevelsDemo.java).

### Что такое уровень изоляции

Уровень изоляции (изоляция / изолированность — буква **I** в **ACID**,
**Isolation**) определяет, **как транзакции могут взаимодействовать между собой**
и насколько сильно могут пересекаться и мешать друг другу при параллельной работе.

Иначе говоря: разные уровни **допускают или не допускают разные аномалии** при
параллельной работе транзакций.

Основных уровней четыре:

1. **READ UNCOMMITTED**
2. **READ COMMITTED**
3. **REPEATABLE READ**
4. **SERIALIZABLE**

### Зачем не обойтись одним уровнем

Почему не взять всегда самый безопасный `SERIALIZABLE` или всегда «среднячок»
`READ COMMITTED`?

Потому что бизнесовые задачи разные:

- где важно сохранять **максимальную целостность** и изолировать транзакции так,
  чтобы они почти не пересекались — цена конфликта/ошибки велика;
- где можно **смириться** с отдельными нестыковками в данных — зато выше
  производительность и можно запускать больше транзакций одновременно.

Повышение isolation само по себе не заменяет защиту инвариантов в SQL
(`SET x = x + 1`, `FOR UPDATE`, `version`) и retry при abort.

### Матрица: какие аномалии на каких уровнях

В зависимости от СУБД возможны нюансы (реализация может быть строже).

| Уровень | Dirty read | Non-repeatable (Fuzzy Read) | Phantom | Типичный default |
|---------|------------|-----------------------------|---------|------------------|
| **READ UNCOMMITTED** | да | да | да | почти нигде |
| **READ COMMITTED** | нет | да | да | PostgreSQL, MS SQL, Oracle |
| **REPEATABLE READ** | нет | нет | да* | MySQL |
| **SERIALIZABLE** | нет | нет | нет | точечно |

\*В **InnoDB** (MySQL) на `REPEATABLE READ` фантомное чтение на практике **не
страшно** — из‑за **MVCC** (см. [§9.6](#96-mvcc)).

Три основные аномалии:

1. **Грязное чтение (Dirty Read)**
2. **Неповторяющееся чтение (Non-repeatable Read / Fuzzy Read)**
3. **Фантомное чтение (Phantom Read)**

На **READ UNCOMMITTED** и **READ COMMITTED** дополнительно возможны:

| Аномалия | Смысл |
|----------|--------|
| **Lost update** (потерянное обновление) | две транзакции одновременно читают и изменяют одни и те же данные, и одно из изменений может потеряться |
| **Out-of-order read** (неупорядоченное чтение) | несколько чтений выполняются в произвольном порядке, что может привести к неправильным результатам в транзакциях |

### 9.1. READ UNCOMMITTED

Это **самый слабый** уровень: транзакция может видеть результаты других
транзакций, **даже если они ещё не закоммичены**.

Пример с балансом:

1. Моя транзакция делает `SELECT` баланса аккаунта 1.
2. Вторая транзакция параллельно **меняет** этот баланс, но **не коммитит**.
3. Даже без коммита второй транзакции мой `SELECT` вернёт **новый изменённый** баланс.
4. Если вторая транзакция **откатит** изменения, и я снова сделаю `SELECT` — получу
   уже **старый** баланс.

Это и есть **Dirty Read (грязное чтение)**: данные, которые я прочитал, кто-то может
**откатить ещё до того, как я завершу свою транзакцию**.

С этим же сценарием связан **Non-repeatable Read (Fuzzy Read)**:

- первая транзакция прочитала баланс и **будет использовать его дальше в логике**;
- параллельно вторая транзакция, несмотря на это, сможет изменить баланс;
- получается, что в своей транзакции я опирался на уже **неактуальные** данные.

Почему аномалия называется «неповторяющееся чтение»: я могу **дважды** прочитать
одни и те же строки в одной транзакции в разное время и получить **разный** результат,
потому что кто-то параллельно изменил данные.

Третья аномалия на этом уровне — **Phantom Read**:

- первой транзакцией я прочитал строки по условию (например, все аккаунты с
  `balance = 0`);
- вторая параллельно **добавила** новый аккаунт с нулевым балансом;
- моя первая транзакция думает, что таких аккаунтов, например, **10**, а по факту
  их уже **11**.

Фантом — когда **ряд данных**, которые я прочитал, кто-то может изменить до того,
как я завершу свою транзакцию (не обязательно «ту же строку», а состав набора).

Итог по уровню: по факту тут **изоляция отсутствует**. Где-нибудь в аналитике
больших данных такой уровень ещё может использоваться, где точность данных не так
важна — но это достаточно редко.

```text
T1:  UPDATE accounts SET balance = 999 WHERE id = 1;   -- без COMMIT
T2:  SELECT balance …                                  -- 999  ← dirty
T1:  ROLLBACK;
T2:  SELECT balance …                                  -- снова старое значение
```

### 9.2. READ COMMITTED

На этом уровне транзакция может читать только те изменения в других параллельных
транзакциях, которые **уже были закоммичены**.

Это **спасает от грязного чтения**, но **не спасает** от неповторяющегося чтения и
от фантомного чтения.

Сценарий:

- теперь я в своей транзакции прочитаю баланс аккаунта, только если он уже
  закоммичен (dirty read закрыт);
- но параллельно другая транзакция может **изменить уже прочитанные мной данные и
  сразу закоммитить**, а моя транзакция всё ещё работает;
- получается: в своей транзакции я всё рассчитываю исходя из одних данных
  (например, баланс = 100), но пока моя транзакция выполнялась, баланс уже стал = 200.

Это снова **Non-repeatable / Fuzzy Read** — уже на «чистых» committed данных.

От **фантомного чтения** уровень тоже не защищает по тем же причинам: два раза в
транзакции делаем один и тот же `SELECT`, но получаем разные результаты, потому что
кто-то между селектами изменил **набор** нужных мне строк.

Такой уровень по умолчанию используется, например, в **PostgreSQL**, **MS SQL** и
**Oracle**.

```text
T1:  SELECT balance WHERE id = 1;          -- 100
T2:  UPDATE … SET balance = 200; COMMIT;
T1:  -- логика всё ещё считает, что 100
T1:  SELECT balance WHERE id = 1;          -- 200  ← non-repeatable

T1:  SELECT … WHERE balance = 0;           -- «их 10»
T3:  INSERT аккаунт с balance = 0; COMMIT;
T1:  SELECT … WHERE balance = 0;           -- «их 11»  ← phantom
```

#### Lost update

На RU и RC дополнительно:

```text
counter = 0
T1 и T2 одновременно читают и потом пишут
-- одно из изменений может потеряться → final не тот, что «сумма» инкрементов
```

Лечение на практике: атомарный `UPDATE … SET x = x + 1`, `FOR UPDATE`, `version`.
В Spring `@Transactional` без явного `isolation` обычно даёт RC.

### 9.3. REPEATABLE READ

Этот уровень означает: **пока транзакция не завершится, никто параллельно не может
изменять или удалять строки, которые транзакция уже прочитала**.

То есть данные, которые я прочитал своей транзакцией, точно никто не изменит, пока
я не завершу свою транзакцию — **по крайней мере, в классическом понимании этого
уровня с блокировками**.

Это спасает и от грязного чтения, и от неповторяющегося чтения.

Но проблему **фантомного чтения** мы всё ещё не решаем. Почему?

- строки, которые я **уже** прочитал, никто не изменит;
- но никто не мешает **добавлять новые** строки параллельно — их мы ещё не читали,
  создавать их ничего не мешает.

```text
T1 @ RR:  SELECT balance WHERE id = 1;     -- 100
T2:       UPDATE … SET balance = 1; COMMIT;
T1:       SELECT balance WHERE id = 1;     -- 100  ← уже прочитанную строку не «увели»

T1 @ RR:  SELECT аккаунты с balance = 0;   -- 10 штук
T3:       INSERT новый аккаунт с balance = 0; COMMIT;
T1:       SELECT … снова;                  -- может стать 11  ← phantom в классической модели
```

Уровень `REPEATABLE READ` используется **по умолчанию в MySQL**.

В **InnoDB** с уровнем `REPEATABLE READ` даже фантомное чтение на практике
**не страшно**. Почему? Там есть **MVCC** — см. ниже.

В PostgreSQL `REPEATABLE READ` — снимок на транзакцию; типичный phantom тоже обычно
не виден — реализация строже упрощённого ANSI.

### 9.4. SERIALIZABLE

Самый жёсткий, но самый **тяжёлый для БД** и **медленный для обработки запросов**
уровень.

Он **блокирует любые действия**, пока запущена транзакция — получается, транзакции
идут **строго одна за другой** и максимально изолируются друг от друга.

Как это достигается:

- с помощью блокировки **всей таблицы** от любых взаимодействий с ней;
- но некоторые СУБД делают менее радикально — блокируют только те **строки**, которые
  задействует текущая транзакция.

Тут никакие аномалии не страшны — ни грязное, ни неповторяемое, ни фантомное чтение.
Но производительность страдает: в такой классической картине транзакции **не могут
работать параллельно**.

В PostgreSQL картина мягче: уровень реализован как **SSI (Serializable Snapshot
Isolation)** на MVCC. SSI работает с конфликтами эффективно, а не жёстко блокирует
диапазоны. При конфликте одна из операций/транзакций может упасть — клиент ретраит
(`SQLState 40001`).

```text
T1 @ SERIALIZABLE:  долгая работа / чтение набора строк
T2:                 пытается менять пересекающиеся данные
-- T2 ждёт / блокируется / либо (в SSI) получает ошибку сериализации
```

Ещё один важный инвариант — **write skew**: две tx по снимку видят «нас двое
on-call» и обе снимают себя с дежурства → 0 on-call. Snapshot/RR это часто не ловит;
`SERIALIZABLE` / явный lock — да.

### 9.5. Выбор уровня

| Сценарий | Уровень |
|----------|---------|
| Целостность критична, пересечения tx дороги | **SERIALIZABLE** (+ готовность к ожиданию/retry) |
| Нужна стабильность уже прочитанных строк | **REPEATABLE READ** |
| Баланс «среднячок» / default многих СУБД | **READ COMMITTED** |
| Точность отдельного чтения вторична (редко) | **READ UNCOMMITTED** |

```java
@Transactional(isolation = Isolation.REPEATABLE_READ)
```

Имеет смысл, если СУБД и connection pool реально это поддерживают.

### 9.6. MVCC

В InnoDB MVCC не допускает фантомное чтение уже на `REPEATABLE READ`; в SQL Server
и PostgreSQL позволяет отдельным уровням изоляции эффективно работать с
параллельными запросами.

**MVCC (Multiversion Concurrency Control)** — метод управления конкурентным доступом
к данным в БД, который позволяет нескольким транзакциям работать с данными
одновременно **без конфликтов** (в смысле блокировок читатель↔писатель). MVCC
поддерживает высокую производительность и изоляцию, **минимизируя блокировки** и
улучшая параллелизм.

#### Многоверсионность

Вместо того чтобы изменять данные **в месте их хранения**, MVCC создаёт **новые
версии** данных.

- Каждая транзакция видит данные в том состоянии, в котором они были **на момент
  начала транзакции**, а не в «текущем» состоянии мира для всех.
- При записи создаётся новая версия строки. В версии есть информация, какая
  транзакция её создала; она становится видимой для транзакций, которые начинаются
  **после** её создания (с учётом правил commit/видимости конкретной СУБД).
- По меткам «кто создал / когда удалили» СУБД определяет, какая версия доступна
  конкретной транзакции.
- Время от времени СУБД очищает старые версии, которые больше не нужны ни одной
  транзакции — **сбор мусора**; это поддерживает эффективность системы.

#### Изоляция через версии

Транзакции видят только те данные, которые были зафиксированы до их начала. В рамках
модели видимости конкретного уровня + MVCC это предотвращает грязное,
неповторяющееся и фантомное чтение.

#### Нет блокировок «чтение vs запись»

Чтение данных не блокирует запись, а запись не блокирует чтение. Отсюда рост
производительности: транзакции могут работать с данными параллельно.

#### Управление конфликтами

Если две транзакции пытаются изменить одну и ту же строку, конфликт решается при
коммите: если одна не может быть закоммичена из‑за конфликта — её можно откатить.

Итого: MVCC позволяет каждой транзакции работать со «своей версией» базы (грубо
говоря), не влияя на остальные и не блокируя данные. Важный момент: MVCC реализован
в разных СУБД **по-разному**; нужно смотреть нюансы конкретной системы.

### 9.7. Другие уровни изоляции

Кроме стандартной четвёрки есть менее популярные уровни.

#### Db2: CURSOR STABILITY и READ STABILITY

Используются в **Db2** (IBM) и дают более тонкую настройку изоляции.

**CURSOR STABILITY (CS).** Блокирует **текущую** строку, прочитанную через курсор
(курсор специально ставят в запросе; он ходит по каждой строке результата по порядку).
С CS блокируем только ту строку, на которой сейчас находится курсор.

**READ STABILITY (RS).** Обеспечивает ситуацию, когда данные, прочитанные одной
транзакцией, **не будут изменены** другой до завершения первой. То есть нет проблемы
неповторяющегося чтения, но **могут быть** фантомные чтения.

Уровни специфичные и актуальны именно для Db2.

#### SQL Server: SNAPSHOT ISOLATION

**SNAPSHOT ISOLATION** (многоверсионная изоляция) позволяет транзакциям видеть
**снимок** базы на момент начала транзакции и тем самым устраняет фантомное и
неповторяющееся чтение, **не блокируя данные при чтении** — это даёт параллелизм
(одновременное чтение одних и тех же данных разными tx). Основа — снова MVCC.

Но Snapshot Isolation **не гарантирует полную сериализуемость**: возможны конфликты
при записи, когда две транзакции пытаются изменить одну и ту же запись — тогда одна
из операций упадёт в ошибку.

#### PostgreSQL: SSI

В PostgreSQL **Serializable Snapshot Isolation (SSI)** тоже работает с версиями и
MVCC. Из‑за этого самый жёсткий и «непараллельный» классический `SERIALIZABLE`
становится намного удобнее: SSI эффективно работает с конфликтами, а не жёстко
блокирует диапазоны.

### 9.8. Как переключить уровень

Конкретный уровень подключают командой вида `SET … ISOLATION LEVEL …`; можно
назначить, **на какие транзакции** он будет действовать.

Пример для `REPEATABLE READ` (MySQL; в других СУБД команды могут отличаться):

```sql
-- будет действовать на 1 следующую транзакцию в текущей сессии
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- будет действовать на все транзакции в текущей сессии
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- вариант включения уровня изоляции в PostgreSQL
SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- будет действовать на все транзакции (глобально)
SET GLOBAL TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

В Java/Spring уровень чаще задают на границе tx
(`Connection.setTransactionIsolation` / `@Transactional(isolation = …)`).

### 9.9. Столкновение tx с разными уровнями

Если параллельно работают несколько транзакций с **разными** уровнями изоляции,
могут возникать проблемы с видимостью данных и появляться те же аномалии. Опять же,
всё зависит от СУБД. Базовые правила:

1. Транзакция с **высоким** уровнем (например, `SERIALIZABLE`) блокирует ресурсы
   более строго → это может привести к блокировкам для tx с более низким уровнем
   (`READ UNCOMMITTED` / `READ COMMITTED`).
2. Если tx с более низким уровнем пытается получить доступ к данным, заблокированным
   более изолированной транзакцией, она **будет ждать**, пока та не завершится
   (или не будет отменена).
3. Транзакция с низким уровнем (`READ UNCOMMITTED`) может видеть **незавершённые**
   изменения других транзакций и не блокирует их → она может прочитать данные,
   которые в итоге будут отменены в более изолированной транзакции.

Практический вывод: без явной схемы не смешивать уровни в одном сценарии; обычно
держат default СУБД и точечно повышают isolation на критичных use-case.

## 11. Вопросы для собеседования и ответы

### 1. Чем candidate key отличается от primary key?

Candidate key — любой минимальный уникальный идентификатор кортежа. Primary key —
тот candidate key, который выбран как основной (для FK, кластеризации в InnoDB и т.д.).
Остальные candidate keys становятся alternate keys и обычно оформляются как `UNIQUE`.
Минимальность обязательна: лишний атрибут в «ключе» делает набор сверхключом
(superkey), но не candidate key.

### 2. Когда брать суррогатный ключ, а когда естественный?

Суррогат — default для OLTP: стабилен, компактен, не зависит от бизнес-переименований.
Естественный — если значение действительно неизменно, уникально и удобно как
идентификатор в интеграциях (ISO-код валюты). Частый паттерн: суррогатный PK +
`UNIQUE(natural_business_key)`.

### 3. Почему M:N нельзя «просто поставить два FK в обе таблицы»?

Кардинальность «многие» с обеих сторон требует множества пар связей. Два поля FK
в родителях выражают только 1:N/1:1. Нужна связующая таблица, где каждая строка —
факт связи (и место для атрибутов связи). Это же отношение нормализует M:N к двум 1:N.

### 4. Дайте точное отличие 3NF и BCNF.

3NF: для каждой нетривиальной FD `X → A` либо `X` — суперключ, либо `A` — первичнó
ключевой атрибут (часть какого-то candidate key). BCNF убирает вторую лазейку:
детерминанта **обязана** быть суперключом. Поэтому бывают схемы в 3NF, но не в BCNF,
когда атрибут candidate key функционально зависит от неключа.

### 5. Зачем денормализуют, если нормализация «правильная»?

Нормализация оптимизирует корректность при обновлениях. Read-heavy сценарии платят
JOIN'ами и сложными агрегатами. Денормализация (кэш-поля, aggregate table, read-model)
ускоряет чтение ценой синхронизации записи. Делают точечно, по профилю нагрузки,
часто вместе с явным владельцем обновления инварианта.

### 6. Почему индекс по `boolean` / полу часто бесполезен, но не всегда?

Селективность низкая: оптимизатор предпочтёт seq scan. Но partial index
(`WHERE active = true` при 1% активных), составной индекс `(status, created_at)`,
bitmap-стратегии в аналитике — могут быть выгодны. Смотрят selectivity + корреляцию
с кластеризацией + реальный план, а не «низкая кардинальность = никогда».

### 7. Чем clustered index в InnoDB отличается от индексов PostgreSQL?

В InnoDB таблица организована как B+tree по PK (clustered): secondary index хранит
ключ PK. В PostgreSQL строки лежат в heap, все индексы указывают на `ctid`;
`CLUSTER` — редкая операция переукладки, не постоянный режим. Путать термины —
частая ошибка на собесе.

### 8. Когда sequential scan выгоднее index scan?

При слабой селективности (нужно много строк), плохой кластеризации (random I/O),
маленькой таблице в кэше, когда стоимость многоблочного чтения меньше суммы
«пройти индекс + достать кучу разбросанных страниц». Оптимизатор сравнивает cost
модели; «всегда использовать индекс» — антипаттерн.

### 9. Чем phantom отличается от non-repeatable read?

Non-repeatable: изменилась **уже прочитанная** строка (UPDATE/DELETE).
Phantom: изменился **набор строк**, удовлетворяющих предикату (INSERT/DELETE
«соседей»). Лечение разное: блокировки строк vs predicate/gap locks или настоящий
serializable/SSI.

### 10. Что гарантирует Read Committed и чего не гарантирует?

Нет dirty read: видны только закоммиченные данные (плюс свои незакоммиченные
изменения). Возможны non-repeatable read, phantoms, lost update на уровне
«прочитал-изменил-записал» без дополнительной защиты. Это разумный default для
многих OLTP-нагрузок при явных инвариантах в `UPDATE`/locks/version.

### 11. Почему в PostgreSQL Serializable могут «падать» транзакции, которые «ничего не ломали» на глаз?

SSI обнаруживает опасные зависимости чтения/записи между concurrent-транзакциями
и абортит одну из них (`serialization_failure`), даже если классических dirty/phantom
на уровне блокировок не видно. Корректный клиент **ретраит** транзакцию. Это цена
семантики «как будто serial», без удержания тяжёлых блокировок на всё подряд.

### 12. Достаточно ли `@Transactional` в Spring, чтобы не было lost update?

Нет. Default isolation (часто RC) не делает read-modify-write безопасным.
Нужны: атомарный SQL, optimistic version, `PESSIMISTIC_WRITE` / `FOR UPDATE`,
или serializable + retry. `@Transactional` задаёт границы и rollback-правила,
но не выбирает стратегию конкурентного контроля за вас.

### 13. Как FK связан с производительностью вставки?

Проверка FK — lookup по индексу родительского ключа (родительский PK/UNIQUE должен
существовать). На горячем write-path это CPU/I/O и потенциальные lock-точки.
Иногда FK снимают в ETL/шардинге, перенося целостность в приложение — ценой риска
«осиротевших» ссылок. Для обычного OLTP FK оставляют: дешевле чинить гонки записи,
чем чинить данные.

### 14. Что важнее на проде: нормальная форма или правильные индексы под запросы?

Это ортогональные оси. Схема без грубых аномалий (≈3NF/BCNF) + индексы/статистика
под реальные запросы + осознанная точечная денормализация. Индекс на плохой схеме
не спасёт от update anomalies; идеальная 5NF без индексов под JOIN убьёт latency.
Смотрят: инварианты → доступ (запросы) → физика (индексы, partitioning).
