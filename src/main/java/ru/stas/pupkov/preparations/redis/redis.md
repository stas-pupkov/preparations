## 1. Что такое Redis

**Redis** — in-memory хранилище структур данных. Часто используют как:

- кэш (ключ → значение + TTL);
- сессии;
- очереди / streams;
- счётчики, rate limit, лидерборды (sorted set);
- pub/sub для уведомлений между нодами.

Данные живут в RAM; на диск можно сбрасывать (RDB/AOF) — это уже про durability, не про
«заменить PostgreSQL».

## 2. Как устроена работа (простая модель)

Классический Redis-сервер обрабатывает команды **в одном основном потоке** (есть I/O
threads в новых версиях, но модель «команда за командой» остаётся простой для головы).

```text
Клиент --GET user:42--> Redis
                         смотрит словарь ключей
                         отдаёт значение из памяти
```

Пример смысла команд:

```text
SET user:42 '{"name":"Ann"}' EX 300   # положить на 5 минут
GET user:42
INCR rate:ip:1.2.3.4                  # атомарный счётчик
HSET order:9 status PAID              # поле в hash
ZADD leaderboard 100 alice            # score в sorted set
```

Почему быстро: нет тяжёлого SQL-оптимизатора на каждый запрос, данные в памяти,
простые операции над ключами.

В Spring Cache Redis часто стоит за `@Cacheable`:

```java
@Cacheable(cacheNames = "users", key = "#id")
public User find(long id) { return repo.findById(id); }
```

Miss → БД → `SET`. Hit → сразу из Redis.

Демо модели кэша без живого Redis: [RedisCacheModelDemo.java](code/RedisCacheModelDemo.java).

## 3. Есть ли блокировки?

### Одна команда

`GET`, `SET`, `INCR` — для клиента выглядят **атомарно**: сервер не «перемешает»
две `INCR` так, что потеряется единица.

### Несколько ключей / шагов

```text
GET stock
(проверили в приложении)
SET stock (новое значение)
```

Между GET и SET другой клиент может влезть → lost update. Это уже не «блокировка Redis»,
а гонка в приложении.

Как делают атомарно:

| Способ | Смысл |
|--------|--------|
| Одна команда | `INCR`, `SET key value NX` |
| `MULTI` / `EXEC` | транзакция: очередь команд, потом выполнить |
| Lua-скрипт | несколько шагов на сервере как одна операция |
| `WATCH` | optimistic: если ключ изменился — `EXEC` отменится |

### Distributed lock

Иногда Redis используют как замок между сервисами (`SET key token NX EX …` + проверка
token при unlock). Это **не** замена блокировкам БД и не серебряная пуля:

- нужен TTL, иначе lock «залипнет» после падения владельца;
- лучше fencing token / идемпотентность работы под замком;
- спорные схемы вроде Redlock на собесе лучше проговаривать с оговорками.

**Итог:** «в Redis есть блокировки?» → команды атомарны; межключевые сценарии — MULTI/Lua;
distributed lock — отдельный хрупкий паттерн, не магия.

## 4. Как выбрать тип кэша

Спроси себя по осям:

| Вопрос | Локальный (Caffeine) | Redis / grid |
|--------|----------------------|--------------|
| Сколько инстансов приложения? | 1 или допустим разный кэш | много, нужен общий вид |
| Нужна ли общая инвалидация? | сложно между нодами | один ключ исчез у всех |
| Latency | микросекунды в процессе | сеть + сериализация |
| Размер данных | ограничен heap процесса | отдельная память Redis |
| Падение кэша | процесс жив, кэш пуст | отдельный failure domain |

Практичные правила:

1. **Один инстанс / sidecar-кэш справочников** → Caffeine (локально).
2. **Несколько нод, один и тот же user-профиль** → Redis.
3. **Очень чувствительные к согласованности деньги** → сначала БД и идемпотентность;
   кэш только для чтения с понятным TTL.
4. **Cache stampede** (все miss разом) → single-flight / soft TTL / прогрев.

Смешанная схема частая: локальный L1 (Caffeine) + L2 (Redis).

## 5. Hazelcast

**Hazelcast** — in-memory data grid: распределённая map, иногда compute near data.

Отличия от Redis на пальцах:

| | Redis | Hazelcast |
|--|-------|-----------|
| Модель | отдельный сервер структур данных | часто Java-кластер / embedded member |
| Клиенты | любой язык, простой протокол | сильная Java-экосистема |
| Кэш в Spring | `RedisCacheManager` | Hazelcast `CacheManager` / map |

Выбор чаще про то, чем команда уже умеет оперировать, а не «кто быстрее в бенчмарке».

## 7. Вопросы для собеседования и ответы

### 1. Redis — это БД?

In-memory store. Может персистить, но типичный прод-кейc — кэш/сессии/счётчики/очереди,
а source of truth остаётся у основной СУБД (если речь про бизнес-данные).

### 2. Почему `INCR` безопаснее «GET + SET +1»?

`INCR` выполняется как одна операция на сервере. GET+SET из приложения — окно гонки.

### 3. Когда Caffeine, когда Redis?

Caffeine — быстро и просто внутри процесса. Redis — общий кэш/состояние между нодами
ценой сети и отдельного сервиса. См. [§4](#4-как-выбрать-тип-кэша).

### 4. Чем Hazelcast отличается от Redis?

Оба закрывают distributed cache. Redis — отдельный сервер структур; Hazelcast ближе к
Java data grid (иногда embedded). Смотрят на стек команды и операционную модель.
