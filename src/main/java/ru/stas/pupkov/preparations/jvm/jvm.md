## 1. За что отвечает JVM

- Загрузка, проверка и исполнение байт-кода;
- Предоставление среды выполнения для байт-кода;
- Управление памятью и очисткой мусора (Garbage Collection).

Виртуальная машина Java (Java Virtual Machine) — механизм, который даёт среду выполнения
для Java-кода и приложений. Это независимая оболочка исполнения: один и тот же байт-код
можно запускать на разных ОС, без прямой зависимости программы от конкретной ОС.

Разделить полезно так:

- **JLS** (Java Language Specification) — правила языка Java;
- **JVMS** (Java Virtual Machine Specification) — правила виртуальной машины и формата
  `.class`;
- **HotSpot** — конкретная реализация JVM в OpenJDK / Oracle JDK.

`javac` превращает исходник в байт-код. JVM этот байт-код исполняет.

## 2. Типы данных

JVM работает с двумя типами данных: примитивные типы (primitive types) и ссылочные типы
(reference types).

### Примитивы

JVM работает с примитивными значениями: целыми числами и числами с плавающей точкой.

В модели байт-кода значения лежат в *слотах*. Обычно слот описывают как 32-битную единицу
в локальных переменных кадра (frame's locals) или в стеке операндов. Поэтому часто говорят:
«по сути JVM — 32-битная машина». Это про **модель вычислений байт-кода**, а не про то, что
процесс HotSpot всегда 32-битный. Современные JDK обычно 64-битные.

Типы `long` и `double` — 64-битные. Они поддерживаются напрямую, но занимают **две** единицы
памяти в locals или в стеке операндов.

Типы `boolean`, `byte`, `short` и `char` при вычислениях обычно работают как 32-разрядные
целые, как `int` (`char` — с нулевым расширением, остальные — со знаковым). Отдельных
инструкций у «маленьких» типов немного: в основном загрузка, сохранение и преобразование.

`boolean` в ряде мест ведёт себя как 8-битный `byte`: `0` — `false`, `1` — `true`.

### Типы ссылок и значения

Есть три вида ссылочных типов:

1. типы классов (class types);
2. типы массивов (array types);
3. типы интерфейсов (interface types).

Их значения — ссылки на динамически создаваемые экземпляры классов, массивы или объекты
классов, реализующих интерфейс.

Сама ссылка в locals / стеке — это не объект. Объект лежит в куче (heap).

```java
String a = "x";
String b = a; // копируется ссылка, не содержимое строки
```

## 3. ClassLoader

Загрузчик классов (ClassLoader) — часть runtime, которая динамически загружает Java-классы
в JVM. Обычно классы грузятся **по запросу**: пока тип не понадобился, его могут ещё не
загружать.

Благодаря ClassLoader система исполнения не обязана сама знать про конкретные файлы и
файловые системы. Загрузчик ищет библиотеки / модули, читает байты и определяет классы.

Важная идея — **делегирование** (parent delegation): перед своей загрузкой loader обычно
спрашивает родителя. Так платформенные классы вроде `java.lang.String` не подменяются из
classpath приложения.

**Класс с данным именем может быть загружен данным загрузчиком только один раз.**
Но другой загрузчик может загрузить «тот же» FQCN (полное имя класса) как **другой** тип.
Идентичность класса в JVM = бинарное имя + defining class loader (определяющий загрузчик).

Демо: [ClassLoaderIdentityDemo.java](code/ClassLoaderIdentityDemo.java).

### Какие загрузчики есть при запуске

В старых текстах (до Java 9) писали про три загрузчика:

1. Bootstrap ClassLoader;
2. Extension ClassLoader;
3. System / Application ClassLoader.

С Java 9 Extension ClassLoader и каталог `jre/lib/ext` убраны. Актуальная картина:

| Загрузчик | Что грузит |
|-----------|------------|
| Bootstrap | классы платформы из модулей JDK (`java.base` и др.). Нативный, в Java виден как `null` |
| Platform ClassLoader | модули платформы, доступные приложению |
| System / Application ClassLoader | код приложения с classpath / module path |

Раньше Bootstrap искали в `<JAVA_HOME>/jre/lib`, а extensions — в `jre/lib/ext` или
`java.ext.dirs`. System ClassLoader брал `java.class.path` / `CLASSPATH` (раньше часто
упоминали `sun.misc.Launcher$AppClassLoader`; сейчас это внутренняя реализация JDK, на имя
класса в коде опираться не стоит).

`ClassLoader.getSystemClassLoader()` — application loader.
`String.class.getClassLoader() == null` — класс загрузил Bootstrap.

### Три действия загрузчика (порядок)

1. **Загрузка (loading)** — найти и импортировать двоичные данные типа.
2. **Связывание (linking)**:
   - **Проверка (verification)** — тип и байт-код корректны;
   - **Подготовка (preparation)** — выделить память под переменные класса и выставить
     значения по умолчанию (`0`, `null`, `false`);
   - **Разрешение (resolution)** — превратить символические ссылки в прямые (может быть
     отложено до первого использования).
3. **Инициализация (initialization)** — выполнить Java-код, который задаёт правильные
   начальные значения (`<clinit>`: static-блоки и инициализаторы static-полей).

Подробнее про фазы — в [разделе 4](#4-жизненный-цикл-класса).

### Пользовательский ClassLoader

ClassLoader написан на Java, поэтому можно сделать свой, не разбирая все детали JVM.
У каждого loader'а есть родитель (parent): его задают при создании или берут loader по
умолчанию.

Свой ClassLoader позволяет:

- загружать и (при подходящих условиях) выгружать классы во время выполнения — в том числе
  с HTTP, из плагина, из сгенерированных байтов;
- менять способ получения байт-кода (например, расшифровка);
- менять байт-код при загрузке (weaving, агенты, AOP).

Типичные сценарии: скриптовые движки, плагины, bean builders, несколько пространств имён
(разные версии одной библиотеки в одном процессе).

Класс можно выгрузить, только когда unreachable (недостижим) его defining class loader.
Утечка loader'а часто приводит к росту Metaspace.

## 4. Жизненный цикл класса

Три крупные фазы по JVMS: загрузка → связывание → инициализация.

### Загрузка

Найти байты типа и создать `Class`. Обычно lazy: пока тип не нужен, его могут не грузить.

### Связывание

1. Verification — проверить class-файл и байт-код.
2. Preparation — выделить память под static-поля и поставить default values.
3. Resolution — разрешить symbolic references из constant pool (сразу или лениво).

На этапе preparation static-поля ещё **не** получают значения из static-блоков. Только
нули / `null` / `false`.

### Инициализация

Здесь выполняется `<clinit>`. Это происходит при *active use* (активном использовании),
например:

- создание экземпляра (`new` и т.п.);
- обращение к static-полю или static-методу (кроме части compile-time констант);
- ряд reflective-сценариев.

Полезно помнить:

- `Class.forName(name, false, loader)` — загрузить/связать **без** инициализации;
- `Class.forName(name)` — по умолчанию ещё и инициализирует.

Демо: [ClassInitializationDemo.java](code/ClassInitializationDemo.java).

Суперкласс инициализируется раньше подкласса.

## 5. Области данных времени выполнения

Run-Time Data Areas — области данных, которые JVM выделяет во время работы программы.

Одни области создаются при старте JVM и живут до её остановки. Другие создаются для каждого
потока и уничтожаются вместе с ним.

```text
                    ┌─────────────────────────────┐
     общие          │  Heap                       │
                    │  Method Area / Metaspace    │
                    │  Run-Time Constant Pool     │
                    └─────────────────────────────┘
                                      ▲
     на поток     ┌─────────┬─────────┴─────────┐
                  │ PC      │ JVM Stack (frames)│  (+ Native Method Stack)
                  └─────────┴───────────────────┘
```

### PC Register

У каждого потока свой PC (program counter, счётчик команд).

Пока поток выполняет Java-метод, PC указывает на текущую инструкцию байт-кода.
Для `native`-метода содержимое PC спецификация описывает слабее.

Коротко: один поток — один PC; создаётся вместе с потоком.

### JVM Stacks

У каждого потока свой стек JVM. В нём лежат frames (кадры).

Стек может быть фиксированного размера или расширяться. Лимит на практике задают через
`-Xss`. Переполнение → `StackOverflowError`. Если стек нельзя создать/расширить из-за
нехватки памяти → `OutOfMemoryError`.

### Heap

Heap (куча) — общая область для всех потоков. Из неё выделяется память под экземпляры
классов и массивы.

Куча создаётся при старте JVM. Объекты явно не освобождают: этим занимается Garbage
Collector. Размер обычно настраивают `-Xms` / `-Xmx`. Память кучи с точки зрения
спецификации не обязана быть одним непрерывным куском.

### Method Area

Method Area (область методов) — общая для всех потоков. Там хранятся структуры класса:
пул констант, данные полей и методов, код методов и конструкторов, служебные методы
инициализации.

В спецификации Method Area логически может считаться частью кучи, но реализация вольна
устроить это иначе.

В HotSpot после удаления PermGen (Java 8) метаданные классов живут в **Metaspace** —
в нативной памяти вне Java heap. Лимит: `-XX:MaxMetaspaceSize`.

Важно не путать:

- объект `java.lang.Class` — в Java heap;
- metadata типа в HotSpot — в Metaspace.

### Run-Time Constant Pool

У каждого класса/интерфейса в runtime есть свой пул констант. Он строится из таблицы
`constant_pool` в `.class`.

Там лежат и простые константы (числа, строки), и символические ссылки на классы, поля и
методы, которые ещё нужно разрешить при выполнении.

По смыслу это похоже на таблицу символов обычного языка, только шире по содержимому.

### Native Method Stacks

Для `native`-методов реализация JVM может использовать обычные «Си-стеки».
Они могут быть отдельными или совмещены с JVM stack — это уже деталь реализации.

### Что ещё встречается на практике

Это не отдельные «обязательные области» из учебника JVMS, но их часто спрашивают:

| Ресурс | Где | Типичная ошибка |
|--------|-----|-----------------|
| Direct ByteBuffer | off-heap / native | `OutOfMemoryError: Direct buffer memory` |
| Стеки потоков | native | много потоков × `-Xss` |
| Code cache (код после JIT) | native | нехватка `-XX:ReservedCodeCacheSize` |
| Metaspace | native | `OutOfMemoryError: Metaspace` |

Демо: [RuntimeDataAreasDemo.java](code/RuntimeDataAreasDemo.java).

## 6. Frames

Frame (кадр стека) хранит данные вызова метода, частичные результаты, помогает
динамическому связыванию, возврату значения и обработке исключений.

Новый frame создаётся при каждом вызове метода. Он уничтожается, когда вызов завершился —
нормально или из-за необработанного исключения.

Frames берутся из стека того потока, который вызвал метод. Чужой поток на этот frame
ссылаться не может.

В каждом frame есть:

1. массив локальных переменных (local variables);
2. стек операндов (operand stack);
3. ссылка на run-time constant pool текущего класса.

Размеры locals и стека операндов известны ещё на этапе компиляции и записаны вместе с кодом
метода.

В каждый момент у потока активен только один frame — текущий. Его метод называют текущим
методом.

### Локальные переменные

Длина массива locals задаётся при компиляции.

Один слот может хранить: `boolean`, `byte`, `char`, `short`, `int`, `float`, reference,
`returnAddress`.  
Пара слотов — `long` или `double`.

Индексация с нуля.

Как передают параметры:

- static-метод — параметры с локальной переменной `0`;
- instance-метод — в `0` лежит `this`, параметры начинаются с `1`.

### Стек операндов

Это LIFO-стек внутри frame. Максимальная глубина тоже известна на compile-time.

При создании frame стек операндов пуст. Инструкции:

- кладут константы и значения из locals / полей;
- снимают операнды, считают, кладут результат обратно;
- готовят аргументы для вызова другого метода и принимают результат.

Пример: инструкция `iadd` ждёт на вершине стека два `int`, снимает их, складывает и кладёт
сумму обратно.

### Динамическое связывание

Frame держит ссылку на run-time constant pool, чтобы разрешать символические ссылки из
class-файла в конкретные классы, поля и методы. Классы при этом могут подгружаться по мере
надобности.

Из-за позднего связывания изменения в других классах реже «ломают» уже скомпилированный
вызывающий код на уровне смещений.

### Нормальное и аварийное завершение

**Нормальное:** метод дошёл до return (подходящего типа). Результат, если есть, попадает в
стек операндов вызывающего frame. Текущий frame отбрасывается, управление возвращается
вызывающему.

**Аварийное (abrupt):** в методе выброшено исключение и не поймано (или явный `throw` ушёл
выше). Значение return вызывающему не возвращается. Frame разрушается, исключение идёт
дальше по стеку.

Глубокая рекурсия → `StackOverflowError`.  
Демо: [StackOverflowDemo.java](code/StackOverflowDemo.java).

## 7. Execution Engine

Байт-код из run-time data areas исполняет execution engine (движок исполнения).
Он читает инструкции и выполняет их.

### Interpreter

Интерпретатор быстро стартует, но на горячем коде обычно медленнее: одни и те же инструкции
снова и снова разбираются и выполняются без полноценной машинной оптимизации метода.

### JIT Compiler

JIT (Just-In-Time) убирает слабое место интерпретатора на горячих местах.

Схема такая:

1. сначала метод часто идёт через интерпретатор и при этом собирается профиль;
2. если метод / цикл горячий, JIT компилирует байт-код в native-код;
3. дальше повторные вызовы используют уже скомпилированный код.

В упрощённых схемах у JIT выделяют:

- генератор промежуточного кода;
- оптимизатор;
- генератор целевого (машинного) кода;
- профилировщик, который ищет hotspot'ы (горячие точки).

В HotSpot на практике важнее знать другое:

- есть **tiered compilation** (многоуровневая компиляция): C1 (быстрее скомпилировать) и
  C2 (сильнее оптимизировать);
- возможна **OSR** (On-Stack Replacement) — компиляция прямо для длинного цикла;
- возможна **deoptimization** — откат, если спекулятивная оптимизация перестала быть верной;
- скомпилированный код лежит в **code cache**.

Типичные оптимизации C2: inlining, escape analysis, устранение лишних блокировок и проверок
на `null`, анализ иерархии классов (CHA).

| | Interpreter | JIT |
|--|-------------|-----|
| Старт | быстрее | нужен прогрев |
| Пиковая скорость на hot path | ниже | выше |
| Цена | CPU на интерпретацию | CPU на компиляцию + code cache |

## 8. Garbage Collection

Garbage Collector автоматически управляет памятью объектов в heap. Конкретный алгоритм JVMS
не фиксирует.

В OpenJDK 17 по умолчанию обычно используют **G1**.

### Поколения

Большинство объектов живут недолго. Поэтому кучу часто делят на young / old (молодое /
старое поколение). Сбор молодых объектов обычно дешевле.

В G1 куча ещё нарезана на regions (регионы).

### Какие сборщики встречаются

| Сборщик | Флаг | Когда уместен |
|---------|------|----------------|
| Serial | `-XX:+UseSerialGC` | маленькие кучи, простые сценарии |
| Parallel | `-XX:+UseParallelGC` | важнее throughput, паузы допустимы |
| G1 | `-XX:+UseG1GC` | баланс пауз и скорости, default в JDK 17 |
| ZGC | `-XX:+UseZGC` | очень короткие паузы, большие кучи |

CMS в актуальных JDK как рабочий выбор уже не рассматривают.

### Идеи G1 коротко

- куча из regions;
- старается сначала чистить regions с большим количеством мусора (garbage-first);
- есть concurrent marking и mixed collections;
- цель по паузе задают `-XX:MaxGCPauseMillis` — это цель, не жёсткая гарантия.

### Reachability

GC считает объект живым, если до него можно дойти из GC roots: локали стеков, static-поля,
JNI-ссылки и т.п.

«Объект стал недостижим» не значит «память освободили в ту же миллисекунду». Он просто
кандидат на сборку.

### Частые сигналы

| Симптом | Куда смотреть |
|---------|----------------|
| `OutOfMemoryError: Java heap space` | утечки, маленький `-Xmx`, лишнее удержание объектов |
| `OutOfMemoryError: Metaspace` | утечка ClassLoader'ов, генерация классов |
| Длинные stop-the-world паузы | выбор GC, размер кучи, allocation rate |
| Высокий allocation rate | лишние временные объекты, боксинг, копирования |

Тюнинг начинают с метрик, а не со случайного набора `-XX:` флагов.

## 10. Вопросы для собеседования и ответы

### 1. Чем JVM отличается от JRE/JDK и от HotSpot?

JVM — абстрактная машина и её контракт (байт-код, области памяти, загрузка классов и т.д.).
HotSpot — реализация этого контракта в OpenJDK. JDK включает компилятор, библиотеки,
инструменты и runtime для запуска. JRE как отдельный дистрибутив в современной модели почти
не выделяют. На собеседовании важно не путать «так написано в JVMS» и «так делает HotSpot».

### 2. Почему фраза «JVM — 32-битная машина» опасна?

В байт-коде locals и стек операндов считаются слотами фиксированной ширины, а `long`/`double`
занимают два слота. Это модель вычислений. Сам процесс HotSpot на 64-bit ОС обычно
64-битный и дополнительно использует compressed oops и нативные указатели. Лучше говорить
про слотовую модель байт-кода, а не про разрядность процесса.

### 3. Что входит в идентичность класса?

Бинарное имя + defining class loader. Два loader'а могут загрузить `com.acme.Plugin` с
одинаковыми байтами — для JVM это разные классы. Cast между ними упадёт. Поэтому плагины
делят общий API через parent loader, а свои реализации грузят отдельно. Демо:
[ClassLoaderIdentityDemo.java](code/ClassLoaderIdentityDemo.java).

### 4. Bootstrap / Platform / App ClassLoader — что изменилось после Java 8?

Extension ClassLoader и `jre/lib/ext` убрали в Java 9. Вместо старой тройки теперь
Bootstrap, Platform и Application ClassLoader. Bootstrap по-прежнему нативный и виден как
`null`. Application ClassLoader грузит приложение. Внутреннее имя класса loader'а — деталь
JDK, в прикладном коде на него лучше не опираться.

### 5. Где выполняется static-блок: loading, linking или initialization?

В фазе initialization, внутри `<clinit>`. Preparation только выставляет значения по
умолчанию. `Class.forName(name, false, loader)` показывает класс без запуска static-блока;
первое active use его запускает. Демо:
[ClassInitializationDemo.java](code/ClassInitializationDemo.java).

### 6. Где «живут классы»: в heap или в Metaspace?

И там, и там, но разное:

- объект `Class` — в Java heap;
- metadata типа в HotSpot — в Metaspace (это реализация Method Area).

Утечка loader'ов бьёт по Metaspace. Удержание миллионов объектов — по heap.

### 7. Из чего состоит frame и зачем нужен operand stack?

В frame есть locals, стек операндов и связь с constant pool. Locals хранят `this`,
параметры и локальные переменные. Operand stack — рабочий стек инструкций байт-кода:
сюда кладут аргументы, отсюда берут операнды для `iadd`, `invoke*` и т.д. Размеры известны
на этапе компиляции метода.

### 8. Чем `StackOverflowError` отличается от `OutOfMemoryError`?

`StackOverflowError` — закончился стек конкретного потока (обычно глубокая рекурсия).
`OutOfMemoryError: Java heap space` — не удалось выделить объект в куче.
Отдельно OOME может случиться при создании потока, если не хватает native-памяти под новый
стек. Это разные бюджеты памяти. Демо: [StackOverflowDemo.java](code/StackOverflowDemo.java).

### 9. Как HotSpot решает, что пора включать JIT?

Считает вызовы и витки циклов, собирает профиль типов и веток. С tiered compilation сначала
работает интерпретатор / C1, горячее уходит в C2. Для длинных циклов возможна OSR. Если
оптимизация оказалась неверной, бывает deoptimization. Готовый код лежит в code cache.

### 10. Почему G1 часто берут по умолчанию, а когда смотрят на ZGC?

G1 хорошо закрывает обычный серверный баланс: паузы умеренные, куча может быть большой,
есть цель `MaxGCPauseMillis`. ZGC берут, когда нужны стабильно очень короткие паузы на
больших кучах и готовы платить накладными расходами. Parallel — когда важнее сырой
throughput. Выбор подтверждают замерами.

### 11. Можно ли выгрузить класс?

Да, но не «любой класс по имени». Обычно класс становится кандидатом на выгрузку, когда
unreachable его defining class loader. Классы из Application ClassLoader приложения на
практике живут всё время процесса. Для плагинов делают короткий lifecycle у child loader'а.

### 12. Что такое resolve symbolic reference и причём тут `NoClassDefFoundError`?

В constant pool лежат символические ссылки. Resolution превращает их в реальные классы /
члены. Если на compile-time зависимость была, а в runtime класса уже нет или он несовместим,
часто видят `NoClassDefFoundError`, `ClassNotFoundException`, `NoSuchMethodError` и другие
linkage errors.

### 13. Зачем parent delegation и когда его ломают?

Delegation защищает платформенные классы и делает namespace предсказуемым: `String` всегда
из Bootstrap. Child-first используют в плагинах, когда нужна своя версия библиотеки, уже
есть у parent. Тогда общие API-типы надо заранее вынести в shared / parent loader, иначе
появятся «два одинаковых класса» и странные `ClassCastException`.
