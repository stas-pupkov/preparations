## 1. Spec-Driven Development (SDD)

**Spec-Driven Development (SDD)** — подход, где **спецификация — источник истины**
(source of truth), а код (часто сгенерированный AI-агентом) — производный артефакт,
который валидируют против этой спеки.

Идея «сначала требования, потом реализация» старая (waterfall, requirements engineering,
ISO/IEC/IEEE 29148). В 2025–2026 она вернулась из‑за coding agents: LLM плохо держит
intent из чата и хорошо следует явному артефакту (обычно Markdown в репозитории).

Инверсия классического потока «сразу в код»:

1. Зафиксировать **что** строить: поведение, ограничения, acceptance criteria, edge cases.
2. Снять неоднозначности (clarify).
3. Спланировать **как**: архитектура, затронутые модули — ещё без кода или почти без.
4. Реализовать (человек / AI / гибрид).
5. Валидировать результат **по спеке**, а не «по ощущениям из чата».

Спека связывает business intent → дизайн → код → тесты. Без неё агент оптимизирует
локально и «дрейфует» от исходного замысла.

## 2. Уровни строгости спеки

| Уровень | Смысл | Когда уместен |
|---------|--------|----------------|
| **Spec-first** | Сначала спека, потом код; спека может устареть | Пилот, одноразовая сложная фича |
| **Spec-anchored** | Спека живёт рядом с изменениями, ревьюят вместе с PR | Типичный прод: фичи средней/высокой сложности |
| **Spec-as-source** | Спека первична; код почти целиком генерируется/пересобирается из неё | Узкие домены с сильной формализацией, генераторы |

На практике чаще **spec-anchored**, а не «водопад на всё» и не полный spec-as-source.

## 3. Типичный lifecycle

Ориентир (Microsoft Spec-Driven Development / Spec Kit и аналоги):

1. **Constitution** — принципы, стандарты, guardrails команды.
2. **Specify** — требования, сценарии, acceptance criteria (что, без лишнего how).
3. **Clarify** — ambiguities, зависимости, edge cases.
4. **Plan** — архитектура, потоки, ограничения, какие файлы/модули затронуты.
5. **Tasks** — атомарные, reviewable единицы работы.
6. **Implement** — генерация/доработка кода и тестов.
7. **Validate** — соответствие спеке (автотесты + human judgment).

Командный вариант review «влево»:

```text
проблема → Markdown-спека (PR) → review «что строим»
       → plan (PR) → review «как»
       → код → validate against spec
```

Дешевле править десятки страниц Markdown, чем тысячи строк после merge.

Содержание спеки (минимум):

- для кого и зачем;
- как должно работать (сценарии);
- in scope / out of scope;
- trade-offs и ограничения (NFR, совместимость, security);
- acceptance criteria / примеры input→output.

## 4. Чем SDD не является

- Не BDD и не TDD сами по себе — хотя Given/When/Then и executable specs хорошо стыкуются.
- Не «огромный SRS до первой строки кода» и не запрет на итерации.
- Не замена дизайну: слабая или двусмысленная спека → уверенный, но неверный код.
- Не обязательный процесс на каждый one-liner / trivial DevOps-тикет.

## 5. Trade-offs и практика внедрения

**Плюсы**

- меньше hallucination и дрейфа агента;
- review смещается влево (intent и план до кода);
- intent переживает сессию чата и смену исполнителя;
- проще онбординг и handoff между людьми и агентами.

**Минусы**

- cost на написание и review спек/планов;
- риск **spec rot** — особенно если в спеку тащат детали реализации;
- выигрыш сильнее на новых фичах и сложной работе, слабее на мелких правках;
- индивидуальный выигрыш от «прояснил перед делегированием»; командный — только если
  SDD стал общим процессом, а не личной привычкой.

Практические правила:

- порог сложности: выше N story points — спека обязательна; trivial / чистый DevOps — опционально;
- спека — living artifact, обновляют при смене intent (не «починили код и забыли»);
- не over-specify слишком рано; детали реализации — в plan/tasks, не обязательно в product-спеке;
- внедрение: pilot на одной фиче → formalize лёгкий шаблон → iterate с AI → refine и scale.

## 6. Экосистема инструментов

| Инструмент / подход | Роль |
|---------------------|------|
| GitHub **Spec Kit** | шаблоны constitution / specify / plan / tasks под агентов |
| Amazon **Kiro** | IDE/workflow вокруг spec-driven цикла |
| **OpenSpec** и аналоги | открытые тулкиты под SDD |
| Кастомные agent skills | ticket (Jira) → диалог → Markdown-спека → plan → code |

Формат почти всегда: Markdown (и иногда structured YAML/JSON) **в git**, ревью через PR.

Связь с соседними практиками:

- **TDD** — executable инварианты на уровне кода;
- **BDD** — сценарии поведения как мост бизнес↔тест;
- **ADR** — решения «почему так», а не полное описание фичи;
- **SDD** — intent и контракт фичи как вход для людей и агентов.

Они дополняют друг друга: narrative/acceptance в спеке, проверка — в тестах, устойчивые
архитектурные выборы — в ADR.

## 7. Вопросы для собеседования и ответы

### 1. Чем SDD отличается от классического requirements engineering и почему идея снова «взлетела»?

Классика тоже требовала спеку до кода, но cost написания и поддержки формальных требований
был высок, а потребитель спеки — человек. С агентами потребитель — LLM: достаточно
ясного Markdown, спеку можно набросать за минуты вместе с тем же агентом, который потом
реализует. Bottleneck сместился с «написать формально» на «удержать intent и не дать
спеке сгнить».

### 2. Где граница между хорошей спекой для агента и over-specification?

Спека должна снимать ambiguity по поведению, scope, NFR и AC. Детали «какой private method
в каком классе» обычно вредят: ускоряют первую генерацию, но ускоряют и rot. Реализационные
детали — в plan/tasks с коротким lifetime. Если спека повторяет код один в один — это уже
второй код на естественном языке.

### 3. Spec-first vs spec-anchored vs spec-as-source — что выбрать?

Spec-first — вход в процесс. Spec-anchored — рабочий режим для продукта: спека в PR рядом
с кодом. Spec-as-source — когда домен узкий и генерация/пересборка из спеки надёжна;
иначе получите дорогой генератор с вечной подгонкой. Для типичного Spring-сервиса —
anchored.

### 4. Как организовать review, чтобы SDD не удвоил bottleneck?

Ревьюить спеку и plan как **дешёвые** артефакты: «верно ли что/как», без style-nits по
прозе. Код-ревью тогда фокусируется на корректности относительно уже согласованной спеки,
безопасности и edge cases, а не на повторном выяснении требований. Не требовать полный
SDD-цикл на тикеты ниже порога сложности.

### 5. Как не превратить SDD в waterfall и dead document после merge?

Короткие итерации, living spec, правило «меняется intent → сначала спека/plan в том же
изменении». Validate закрывает петлю: расхождение чинят либо в коде (спека верна), либо
в спеке (спека устарела) — осознанно, не «поправили код и забыли». Не блокировать spike:
spike → выводы → спека → реализация.

### 6. Как стыковать SDD с TDD/BDD и ADR?

SDD фиксирует intent и AC. BDD/сценарии могут быть частью спеки или executable слоем
поверх неё. TDD закрепляет инварианты в коде. ADR фиксирует архитектурные развилки
(«выбрали outbox, а не 2PC»). Single source of truth по поведению фичи — спека (+ тесты
как проверка); ADR — по решениям «почему так устроено».
