## 1. Что такое Kafka и когда её брать

Apache Kafka — распределённый **commit log** / платформа потоковой передачи событий.
Сообщения пишутся в append-only лог, хранятся заданное время (или до лимита размера) и
читаются независимо многими consumer'ами.

Сильные стороны:

- высокая пропускная способность и горизонтальное масштабирование через партиции;
- персистентность и возможность **перечитать** историю (пока жив retention);
- независимые consumer group на одном топике (fan-out без копирования очереди);
- экосистема: Connect, Streams, Schema Registry.

Чего нет «из коробки» как у классического брокера:

- DLQ / delayed / priority queues как first-class модель;
- AMQP/MQTT-семантика;
- гибкий broker-side routing по произвольным заголовкам (это делают приложением или Connect).

Брать Kafka, когда нужны поток событий, высокая нагрузка, несколько независимых читателей,
replay и интеграция в data platform. Брать очередь (RabbitMQ и аналоги), когда важны
простой routing, конкурирующие воркеры на одном потоке без партиционирования, небольшая
нагрузка и короткая жизнь сообщения.

## 2. Основные компоненты

| Компонент | Роль |
|-----------|------|
| **Broker** | Узел кластера: принимает запись, хранит логи партиций, отдаёт данные consumer'ам |
| **Topic** | Логический канал/категория сообщений |
| **Partition** | Упорядоченный неизменяемый лог внутри топика; единица параллелизма |
| **Producer** | Пишет записи в топик |
| **Consumer** | Читает записи (обычно в составе consumer group) |
| **Consumer group** | Набор consumer'ов с одним `group.id`; партиции делятся между членами группы |
| **Controller / KRaft** | Управление метаданными кластера |

### Record

Запись в логе: optional `key`, `value`, headers, timestamp, `offset` (назначает брокер
внутри партиции), `partition`.

### Метаданные и маршрутизация клиента

Центрального прокси в Kafka нет: **клиент сам** выбирает, к какому брокеру слать
Produce/Fetch. Карта кластера (брокеры, топики, лидер каждой партиции) приходит через
Metadata API. `bootstrap.servers` — только точки входа за первой картой; достаточно
одного живого адреса из списка, дальше клиент ходит к лидерам напрямую и кэширует
топологию в памяти.

Кэш считается верным, пока нет сигнала об устаревании:

| Триггер | Смысл |
|---------|--------|
| `NotLeaderForPartition` | Запрос ушёл не к текущему лидеру |
| `UnknownTopicOrPartition` | Топик/партиция ещё не известны брокеру (свежий топик, неверный номер) |
| Обрыв соединения | Брокер недоступен → метаданные с другого узла |
| `metadata.max.age.ms` | Проактивный refresh без ошибки (иначе не увидеть, например, новые партиции) |

Единичные всплески этих ошибок после рестарта брокера или смены числа партиций —
ожидаемы. Постоянный поток — почти всегда сеть или неверные адреса в метаданных.

**`listeners` vs `advertised.listeners`.** `listeners` — на каких интерфейсах брокер
слушает. `advertised.listeners` — что он **сообщает клиентам** в MetadataResponse.
В Docker/Kubernetes/NAT/облаке типичный инцидент: брокер отдаёт внутренний адрес
(`kafka.internal:9092`), снаружи недоступный → клиент «потерял кластер», хотя брокеры
живы. Симптом: бесконечные коннекты к хосту, которого клиент «узнал» из метаданных,
а не из `bootstrap.servers`.

## 3. Topic, partition, log, segment

### Архитектура топика

- Топик = набор партиций.
- Партиция = упорядоченный лог на диске; запись только в конец.
- Лог режется на **сегменты** (segment files). Пишут в **активный** сегмент; закрытые —
  пассивные.
- Поиск по offset быстрый за счёт индексных файлов рядом с сегментом.

### Retention и удаление

Политика `cleanup.policy`:

- `delete` — удаление старых данных по времени (`retention.ms`) и/или размеру
  (`retention.bytes`);
- `compact` — log compaction: для каждого ключа стремится оставить последнее значение;
- допустима комбинация `compact,delete`.

Важный нюанс: при `delete` Kafka **не удаляет отдельные сообщения по одному**.
Удаляется **целый сегмент**, когда он закрыт и «протух» относительно последнего сообщения
в сегменте. Поэтому фактическое хранение часто чуть дольше формального `retention.ms`.

Сегмент закрывается по размеру (`segment.bytes`, часто ~1 GiB) или по времени
(`segment.ms`).

### Compaction

Для changelog / «текущее состояние сущности» (`userId → profile`). Cleaner периодически
переписывает сегменты, выкидывая устаревшие версии ключа. `value = null` — **tombstone**:
ключ помечается к удалению. Параметры вроде `min.compaction.lag.ms` задают, как рано
можно компактить свежие записи.

Демо моделей: [SegmentRetentionDemo.java](code/SegmentRetentionDemo.java),
[LogCompactionModelDemo.java](code/LogCompactionModelDemo.java).

### Ключевые настройки топика

| Параметр | Смысл |
|----------|--------|
| `num.partitions` | Число партиций (увеличивать можно; уменьшать — почти всегда боль) |
| `replication.factor` | Число реплик партиции |
| `min.insync.replicas` | Минимум ISR для успешной записи при `acks=all` |
| `retention.ms` / `retention.bytes` | Срок / объём хранения при delete |
| `cleanup.policy` | `delete` / `compact` / оба |
| `segment.bytes` / `segment.ms` | Границы сегментов |

## 4. Репликация и отказоустойчивость

- У каждой партиции есть **leader** и набор **followers** (реплик).
- Producer пишет в leader; followers реплицируют лог.
- **ISR** (in-sync replicas) — реплики, не отстающие от лидера сверх допустимого лага.
- При падении лидера контроллер выбирает нового лидера из ISR (если
  `unclean.leader.election.enable=false` — предпочтительный production-default).
- `acks=all` + достаточный `min.insync.replicas` — запись считается успешной только после
  подтверждения от ISR-кворума; это база durability.
- **Unclean leader election** повышает availability ценой возможной потери уже
  «подтверждённых» данных — на проде обычно выключен.

Дополнительно: MirrorMaker 2 для репликации между кластерами; rack-awareness
(`broker.rack` / `client.rack`) для размещения реплик и предпочтения локальных fetch.

## 5. Producer

Путь записи:

1. Сериализация key/value.
2. Выбор партиции: явный номер / `Partitioner` / hash ключа / sticky без ключа.
3. Буферизация в batch (`batch.size`, `linger.ms`, `buffer.memory`).
4. Опциональное сжатие (`compression.type`: snappy, lz4, zstd, gzip).
5. Отправка на leader; ожидание ack по политике `acks`.
6. Retry при retriable ошибках; при `enable.idempotence=true` — без дублей в логе.

### `acks`

| Значение | Поведение |
|----------|-----------|
| `0` | Не ждёт ack — максимум скорости, риск потери |
| `1` | Ack от leader |
| `all` / `-1` | Ack от всех ISR (с учётом `min.insync.replicas`) |

### Идемпотентный producer

`enable.idempotence=true` (в современных клиентах часто уже default-friendly вместе с
безопасными `acks`/`retries`): брокер дедуплицирует записи по **PID + sequence number**.
Это **exactly-once запись в лог при retry**, а не «сообщение обработано ровно один раз
на стороне consumer».

### Транзакции

Transactional producer (`transactional.id`) даёт атомарную запись в несколько партиций/топиков
и связку read-process-write в EOS-пайплайнах (вместе с `isolation.level=read_committed` на
consumer). Это другой уровень, чем одна только идемпотентность.

### Важные тюнинги

- `bootstrap.servers` — точки входа за метаданными, не «все брокеры обязательно»;
- `retries` / `delivery.timeout.ms` / `request.timeout.ms` — бюджет доставки;
- `max.in.flight.requests.per.connection` — при идемпотентности ограничение совместимо с
  порядком (клиент сам следит за контрактом);
- `partitioner.class` — кастомная логика; без ключа в новых клиентах sticky batching.

### Лимиты размера сообщения (каскад)

Дефолтный потолок на брокере порядка ~1 MiB (`message.max.bytes`). Превышение →
`RecordTooLargeException`. Крупные записи бьют по throughput, GC, репликации и
восстановлению брокера — поэтому лимит выбран сознательно.

Лимиты **каскадные** и должны быть согласованы на всём тракте:

| Где | Параметр |
|-----|----------|
| Брокер | `message.max.bytes` |
| Репликация | `replica.fetch.max.bytes` |
| Producer | `max.request.size` |
| Consumer | `fetch.max.bytes`, `max.partition.fetch.bytes` |

Типичный прод-баг: producer поднял `max.request.size`, consumer оставил маленький
`fetch.max.bytes` → запись есть, чтение встаёт. Поднимать размеры нужно синхронно
на всех сторонах.

## 6. Consumer, consumer group, offset

### Модель чтения

Kafka — **pull**: consumer сам запрашивает данные (`poll` → Fetch), контролируя скорость.
Это не push-брокер в духе классического AMQP: брокер не «пушит» сообщения клиенту.

Внутри одной **consumer group**:

- каждая партиция назначена **ровно одному** consumer'у группы;
- consumers &lt; partitions → у части consumers несколько партиций;
- consumers &gt; partitions → лишние **простаивают**, пока кто-то не отвалится или не
  добавят партиции.

Независимых групп на одном топике может быть сколько угодно: каждая получает **полный**
поток (pub-sub на уровне групп). Внутри группы — семантика конкурирующей обработки
партиций (queue-like на уровне partition assignment).

Демо: [ConsumerGroupAssignmentDemo.java](code/ConsumerGroupAssignmentDemo.java).

### Long polling и purgatory

Пустой Fetch при отсутствии новых данных был бы дорог. Long polling: брокер
**придерживает** ответ, пока не наберётся объём или не истечёт ожидание.

- `fetch.min.bytes` — минимум данных в ответе;
- `fetch.max.wait.ms` — максимум удержания на брокере.

Отложенный Fetch живёт во внутренней очереди ожидания (**purgatory**): между
«выполнен» и «отклонён», пока не сработает условие. Данных сразу достаточно —
ответ без очереди. Trade-off: меньше пустых round-trip, но при низкой нагрузке
и завышенном `fetch.min.bytes` события «запаздывают», пока брокер ждёт пачку.

Лимиты одного Fetch: `fetch.max.bytes` (весь запрос) и `max.partition.fetch.bytes`
(на партицию). Их нужно держать согласованными с лимитами записи
([§5](#лимиты-размера-сообщения-каскад)).

### Offset

Offset — монотонный номер записи **внутри партиции**. Группа коммитит прогресс
(обычно в топик `__consumer_offsets`). После рестарта чтение продолжается с
committed offset (следующая позиция).

Пока данные не вытеснены retention/compaction, offset можно **сдвинуть назад** и
перечитать (CLI `kafka-consumer-groups`, AdminClient, `seek`).

`auto.offset.reset` (`earliest` / `latest` / `none`) срабатывает, когда для группы
**нет** валидного committed offset (новый group или offset вычищен).

### `subscribe` / `poll` / `commit`

- `subscribe(topics)` — вступить в группу, получить assignment от координатора;
- `assign(partitions)` — ручное назначение без group protocol (другой режим);
- `poll(Duration)` — забрать батч; здесь же крутятся heartbeat/rebalance callbacks
  в классическом sync-consumer;
- `commitSync` / `commitAsync` — ручная фиксация offset при `enable.auto.commit=false`.

`commitSync` — блокируется, ретраит до успеха или фатальной ошибки; надёжнее на
критичном пути «зафиксировать перед выходом».
`commitAsync` — без ожидания, выше throughput, при ошибке сам не ретраит так же
агрессивно; часто комбинируют: async в цикле + sync на rebalance/shutdown.

### Group coordinator, JoinGroup / SyncGroup, generation

- **Group coordinator** — брокер, ведущий membership группы, heartbeat и хранение
  offset'ов группы. Клиент находит его через `FindCoordinator` по `group.id`.
- В **classic rebalance protocol** один из consumer'ов становится **group leader** и
  считает assignment; это не «лидер, который раздаёт offset другим». Offset коммитят
  сами consumer'ы координатору.

Классический цикл (упрощённо):

1. Members шлют `JoinGroup`; координатор ждёт всех активных и запускает rebalance.
2. Один member — group leader — получает список членов и строит assignment
   (стратегия `partition.assignment.strategy`).
3. Все шлют `SyncGroup`; лидер вкладывает план, остальные — пусто.
4. Координатор раздаёт каждому его партиции → группа Stable.

Каждый успешный цикл поднимает **`generation.id`**. `OffsetCommit` несёт поколение:
commit от устаревшего generation → `ILLEGAL_GENERATION`. Так member прошлого
поколения не перезапишет offset после потери членства.

Два параллельных контура: основной поток делает `poll`/обработку; фоновый —
heartbeat координатору. Heartbeat ещё и обратный канал: в ответе может прийти
сигнал вроде `REBALANCE_IN_PROGRESS` — пора переприсоединяться.

- `session.timeout.ms` — жив ли member для координатора (пропали heartbeat).
- `max.poll.interval.ms` — не застряла ли обработка (heartbeat идут, а `poll` давно
  не вызывался). Это **разные** таймеры; путать их — частая ошибка на собесе и в проде.

### Static membership (`group.instance.id`)

По умолчанию member динамический: ушёл → сразу выкинули → вернулся как новый →
rebalance. При частых рестартах (деплой, rolling restart) это даёт шторм.

**Static membership** (KIP-345): стабильный `group.instance.id` на инстанс.
Координатор при кратком исчезновении не рвёт группу сразу, а ждёт возвращения
того же ID в пределах `session.timeout.ms`. Успел вернуться — те же партиции без
полного rebalance. Типичный приём для stateful consumer'ов и частых рестартов подов.

## 7. Порядок обработки

Гарантии Kafka:

- **строгий порядок только внутри одной партиции**;
- между партициями порядка нет;
- в группе одну партицию читает один consumer → последовательное чтение offset'ов
  сохраняет порядок **если обработка в consumer'е тоже последовательна** (не уводить
  записи в неупорядоченный пул потоков без барьеров).

Чтобы связанные события (операции по одному счёту) обрабатывались по порядку, они
должны попасть в **одну партицию**. Практический приём: один и тот же key
(`accountId`) → hash(key) % N. Пока N не меняют, ключ остаётся на той же партиции.

Увеличение `num.partitions` ломает привязку key→partition для части ключей: старые
данные остаются в старых партициях, новые с тем же ключом могут пойти в другую.
Это важный operational trade-off.

Если порядок не нужен (логи, метрики) — важнее равномерность: sticky / round-robin /
аккуратный ключ с хорошей кардинальностью.

Демо: [KeyBasedPartitioningDemo.java](code/KeyBasedPartitioningDemo.java).

## 8. Семантики доставки

Семантика отвечает на вопрос: **сколько раз сообщение может быть доставлено/обработано
при сбоях** — 0..1, ≥1 или «ровно один раз». Важно сразу зафиксировать границу:
«доставлено» *куда*? В лог Kafka, в обработчик consumer'а или во внешнюю систему
(БД, HTTP, другая очередь)? От границы зависят и механизмы, и честный ответ на собесе.

| Семантика | Смысл | Типичная цена |
|-----------|--------|----------------|
| **At-most-once** | 0 или 1 раз | возможна **потеря**, дублей нет |
| **At-least-once** | ≥ 1 раза | **дубли** возможны, потерь при корректной схеме нет |
| **Exactly-once** | эффект ровно один раз | сложнее; зависит от границы системы |

Ниже — полный путь: producer → брокер → consumer → побочный эффект.

### 8.1. Полный путь сообщения

```text
[приложение A]
    → serialize + выбрать партицию
    → batch в буфере producer'а
    → send на leader партиции
    → репликация в ISR / ack по политике acks
    → запись появляется в логе (offset N)
[приложение B, consumer group]
    → poll: забрать записи с позиции group
    → обработать (БД / HTTP / запись в другой топик)
    → commit offset (следующая позиция для группы)
```

Сбои возможны на каждом шаге. Семантика — это соглашение, **что допустимо**, когда
сеть оборвалась, процесс умер или rebalance забрал партицию посередине цикла.

### 8.2. Сторона producer: как запись попадает в лог

1. `send` кладёт запись в буфер; реально уходит batch.
2. Leader пишет в свой лог и (при `acks=all`) ждёт ISR.
3. Брокер отвечает ack. Если ack **потерялся**, а запись уже легла — producer не знает
   результата и при `retries > 0` отправит **ещё раз**.

Без идемпотентности повтор = **вторая запись в логе** с новым offset (дубль payload).
С `enable.idempotence=true` у producer есть PID и sequence number; брокер узнаёт повтор
того же `(PID, seq)` и не пишет второй раз. Это **exactly-once запись в лог при retry**,
а не «система обработала событие ровно один раз».

Связка durability:

- `acks=0` — не ждём ack → максимум скорости, легко потерять до попадания в лог;
- `acks=1` — ack от leader; падение leader до репликации может потерять хвост;
- `acks=all` + `min.insync.replicas` — запись подтверждена кворумом ISR.

Транзакционный producer (`transactional.id`) группирует несколько записей (и иногда
commit offset'ов) в атомарную транзакцию: либо видны все, либо ни одной (для
`isolation.level=read_committed` на consumer'е).

Демо retry: [ProducerRetrySemanticsDemo.java](code/ProducerRetrySemanticsDemo.java).

### 8.3. Сторона consumer: poll → process → commit

В группе у каждой партиции свой committed offset — «с какого offset читать дальше».
Типичный цикл:

1. `poll` — получить батч, сдвинуть **локальную** позицию чтения в клиенте.
2. Обработать записи.
3. `commit` — сохранить прогресс группы (обычно в `__consumer_offsets`).

Семантика consumer'а почти всегда сводится к **моменту commit относительно обработки**.

```text
at-most-once:   poll → commit → process
at-least-once:  poll → process → commit
```

Auto-commit (`enable.auto.commit=true`) коммитит по таймеру «что уже отдали в poll»,
часто **до** того, как прикладной код закончил работу → ближе к at-most-once по риску
потерь при падении.

### 8.4. At-most-once — от начала до конца

Цель: никогда не обработать дважды; потеря допустима.

Примерный сценарий:

1. Producer шлёт с умеренными гарантиями (иногда даже `acks=1` / мало ретраев) —
   запись может не попасть в лог, и бизнес это принимает.
2. Consumer: после `poll` сразу commit (или auto-commit), потом обработка.
3. Процесс умер на обработке записи B, offset уже закоммичен за B.
4. Новый consumer группы начинает с следующей позиции → **B потеряна**.

Когда так делают: метрики, логи, события, где дырка лучше дубля. На деньгах и
изменении состояния счёта — обычно нет.

Демо: [DeliverySemanticsDemo.java](code/DeliverySemanticsDemo.java) (`commit` до process).

### 8.5. At-least-once — от начала до конца

Цель: не потерять; дубль допустим (его должны пережить).

Сценарий на producer:

1. Запись попала в лог, ack потерялся → retry.
2. Без идемпотентности в логе два одинаковых payload → consumer увидит оба.
3. С идемпотентностью в логе одна запись → дубль на этом этапе снят.

Сценарий на consumer (самый частый на собесе):

1. `poll` получил A, B.
2. Успешно обработали A, B (записали в БД).
3. Commit не успели — процесс убит / rebalance.
4. Другой member читает снова с старого offset → **A и B обработаются ещё раз**.

Демо: [DeliverySemanticsDemo.java](code/DeliverySemanticsDemo.java) (`commit` после process).

Практический каркас consumer'а:

```text
while running:
  records = poll()
  for record in records:
      processIdempotently(record)   // побочный эффект безопасен при повторе
  commitSync()                      // или async + sync на shutdown/rebalance
```

### 8.6. Exactly-once — что реально обещают

Слова «exactly-once» без границы — ловушка. Разложим по уровням.

**Уровень 1 — запись в лог Kafka**

Idempotent producer: одна логическая отправка при retry → одна запись в партиции.

**Уровень 2 — пайплайн Kafka → Kafka (read-process-write)**

Transactional producer + consumer с `isolation.level=read_committed`:

1. Читаем из входного топика.
2. Пишем результат во выходной топик **в той же транзакции**.
3. Commit offset'ов входной группы тоже входит в транзакцию (через API sendOffsetsToTransaction).
4. Либо видны и выходные записи, и новый offset; либо при сбое — откат, повтор чтения.

Так работают Kafka Streams в EOS-режиме и аккуратные ETL «топик в топик».
Consumer с `read_uncommitted` может увидеть ещё не зафиксированные транзакционные записи.

**Уровень 3 — побочный эффект вне Kafka (БД, HTTP, почта)**

Kafka **не** делает внешний UPDATE «ровно один раз» сама по себе. Нужен один из паттернов:

- идемпотентный обработчик (уникальный `eventId` / business key);
- **Transactional Outbox**: в одной DB-транзакции меняем состояние и пишем событие в
  outbox-таблицу; отдельный процесс публикует в Kafka;
- inbox / дедуп-таблица: «этот message id уже применён» — skip;
- реже — распределённые трюки с 2PC-подобными схемами (дорого и хрупко).

Формула для собеса:

```text
exactly-once эффект ≈
    at-least-once доставка
  + идемпотентная (или транзакционно связанная) обработка
```

или, для чистого Kafka→Kafka:

```text
transactions + read_committed (+ idempotent producer)
```

### 8.7. Как выбрать семантику

| Ситуация | Обычно |
|----------|--------|
| Счётчики, логи, телеметрия | at-most-once или at-least-once без жёсткой дедупликации |
| Деньги, статусы заказа, «списать один раз» | at-least-once + идемпотентность / outbox |
| Обогащение топика → другой топик | транзакции Kafka (EOS) |
| «Нам сказали включить exactly-once в Spring и всё» | уточнить границу; часто нужен дизайн приложения |

Связка с другими разделами: durability записи — [§4](#4-репликация-и-отказоустойчивость)
и [§5](#5-producer); commit/rebalance — [§6](#6-consumer-consumer-group-offset) и
[§9](#9-rebalance).

## 9. Rebalance

Rebalance — перераспределение партиций между members группы. Триггеры: join/leave,
падение member, подписка на новые топики, изменение числа партиций, истечение
session / max.poll.interval. Протокол JoinGroup/SyncGroup и `generation.id` —
в [§6](#group-coordinator-joingroup--syncgroup-generation).

Протоколы:

- **Eager** — на время rebalance все партиции отзываются (stop-the-world для обработки);
- **Cooperative sticky** — отзываются только те партиции, которые реально надо отдать;
  меньше «шторма» и простоя.

Антипаттерн **rebalancing storm**: нестабильные инстансы, слишком агрессивные таймауты,
долгая обработка при маленьком `max.poll.interval.ms`, частый деплой без graceful
shutdown (`wakeup`/`close`). Смягчение рестартов: static membership
([§6](#static-membership-groupinstanceid)).

Типичный цикл шторма: обработка батча дольше `max.poll.interval.ms` → member сам
покидает группу → другой берёт те же партиции → снова не укладывается → бесконечный
rebalance. Лечение: ускорить process, уменьшить `max.poll.records`, поднять
`max.poll.interval.ms` под реальное время батча.

## 10. Типичные проблемы

| Проблема | Суть | Куда смотреть |
|----------|------|----------------|
| Message duplication | at-least-once, retry, rebalance mid-batch | идемпотентность, ключ дедупа, транзакции |
| Consumer lag | обработка медленнее produce | партиции, concurrency, batch, узкое место в коде/БД |
| Hot partition | перекос ключей | кардинальность ключа, custom partitioner |
| Stuck partition | блокировка на одном сообщении | таймауты, poison pill / DLQ-паттерн снаружи, изоляция тяжёлой работы |
| Rebalance storm | thrashing assignment | session/poll interval, static membership, cooperative |
| Under-replicated | реплики отстают | диск/сеть, нагрузка, ISR |
| «Кластер мёртв», брокеры живы | клиент ходит не туда | `advertised.listeners`, сеть, устаревшие метаданные |
| Всё OK, но медленно | silent throttling по квоте | `produce/fetch-throttle-time-avg` |

Lag Kafka **сама не «лечит»** — даёт метрики (consumer group lag, AdminClient). Решение —
масштаб и оптимизация consumer path.

Head-of-line blocking: один «ядовитый» record останавливает всю партицию для этого
consumer'а. В классической модели конкурирующие consumer'ы **не** разбирают одну
партицию по сообщениям. В новых версиях Kafka развивается модель share groups / queues
(KIP-932 и продолжения) — имеет смысл знать как тренд, на собесе уточнять версию
кластера.

### Квоты и throttling

Брокер может ограничивать клиента по пропускной способности и доле CPU. При превышении
квоты **ошибки часто нет**: в ответе приходит `ThrottleTimeMs`, клиентская библиотека
искусственно замедляется. Снаружи — рост latency при нулевом error rate.

Куда смотреть: клиентские метрики `produce-throttle-time-avg`, `fetch-throttle-time-avg`.
Ненулевые значения = брокер намеренно тормозит. Особо опасно для async producer:
буфер забивается → после исчерпания `buffer.memory` `send()` блокируется, приложение
перестаёт принимать вход. При разборе «всё успешно, но тормозит» throttle-метрики —
первый чеклист, не последний.

## 11. Почему Kafka быстрая

Коротко: Kafka не пытается быть «умной очередью на каждое сообщение». Она пишет и читает
**большой последовательный лог** так, как любит диск и ОС.

### 1. Append-only лог

Новые записи только **добавляются в конец**. Нет поиска «куда воткнуть» и нет удаления
отдельного сообщения в горячем пути. Диск любит последовательную запись сильнее, чем
случайные правки по всему файлу.

### 2. Сегменты и простой поиск

Партиция = цепочка файлов-сегментов. Offset → нужный сегмент находится по индексу рядом
с данными. Читать «с позиции N» дёшево.

### 3. Работа с байтами, не с объектами

Брокер **не знает** про JSON/Avro/поля домена: в логе лежат opaque **byte arrays**
(key/value/headers). Сериализация — на **Producer** (`Serializer`), десериализация — на
**Consumer** (`Deserializer`). Брокер не парсит payload, не валидирует схему и не гоняет
объекты через свою JVM-кучу на каждый record — только пишет/читает/реплицирует байты.
Отсюда дешевизна горячего пути и возможность zero-copy. Контракт «что внутри байтов»
живёт у клиентов (+ Schema Registry снаружи, если нужен).

### 4. Page cache ОС

Данные часто уже лежат в **кэше страниц ОС** (page cache). Consumer читает «с диска», но
реально часто из RAM. Kafka опирается на это вместо своей огромной кучи объектов в JVM.

### 5. Batch

Producer собирает много записей в batch (`batch.size`, `linger.ms`). По сети и на диск
уходит пачка, а не тысяча мелких syscalls. Consumer тоже забирает пачками (`max.poll.records`,
fetch size).

### 6. Zero-copy (где доступно)

При отдаче данных клиенту брокер может отдавать байты из page cache в сокет почти без
лишнего копирования в user-space (идея `sendfile` / zero-copy). Меньше CPU на копирование
буферов. Это возможно именно потому, что брокер оперирует байтами, а не десериализованными
объектами.

### 7. Параллелизм партициями

Топик режется на партиции → разные брокеры и consumer'ы работают **параллельно**. Узкое
место — не «один глобальный lock на всю очередь», а конкретная партиция.

### 8. Pull, а не push

Consumer сам говорит «дай ещё», когда готов. Медленный consumer не заставляет брокер
держать сложную per-consumer очередь доставки в памяти так же, как классический push-брокер.

**Итог на собесе:** быстрая не потому что «всё в RAM», а потому что последовательный лог +
байты без parse на брокере + batch + page cache + партиции + простая модель хранения.

## 12. Streams, Connect, Schema Registry

Кратко — чтобы не путать слои:

- **Consumer API** — «прочитать и сделать что угодно»;
- **Kafka Streams** — библиотека в процессе приложения: DSL/Processor API, state stores,
  windowing, запись обратно в Kafka; отдельный кластер обработки не нужен;
- **Kafka Connect** — фреймворк source/sink коннекторов без своего кода на каждый ETL;
- **Schema Registry** — версии схем (Avro/Protobuf/JSON Schema), совместимость
  producer/consumer при эволюции контракта.

Версионирование сообщений сама Kafka «по полям» не ведёт: либо поле version в payload,
либо схема в Registry + совместимость (BACKWARD/FORWARD/FULL).

## 13. Kafka vs RabbitMQ

**Kafka — это журнал событий. RabbitMQ — это брокер очередей.** Из этой разницы
следует почти всё остальное.

### Как устроены

**Kafka** пишет сообщения в конец длинного журнала. Журнал режется на части
(партиции), чтобы читать и писать параллельно. Consumer сам забирает данные,
когда готов. Сообщения лежат столько, сколько настроено хранение — их можно
перечитать заново.

**RabbitMQ** кладёт сообщение в очередь. Брокер обычно сам отдаёт его работнику.
После подтверждения обработки сообщение, как правило, исчезает. Повторно
«проиграть историю» для всех желающих так же удобно нельзя.

### Как масштабируется обработка

В Kafka внутри одной группы consumer'ов каждую партицию читает только один
consumer. Хочешь больше параллелизма — нужно больше партиций. Лишние
consumer'ы будут простаивать. Если одно сообщение «застряло», оно тормозит весь
хвост своей партиции.

В RabbitMQ несколько работников просто разбирают сообщения из одной очереди.
Добавил воркера — он сразу начинает брать задачи, без увеличения числа партиций.

### Сравнение

| Критерий | Kafka | RabbitMQ |
|----------|-------|----------|
| Модель | журнал событий, consumer забирает сам | очереди и обменники, брокер чаще сам отдаёт |
| Хранение | заданный срок/объём, можно перечитать | обычно до подтверждения, затем удаление |
| Масштаб | партиции, высокая пропускная способность | проще при умеренной нагрузке |
| Маршрутизация | топики + логика в приложении / Connect | обменники и ключи маршрутизации «из коробки» |
| Конкуренция воркеров | по партициям (одна партиция — один consumer в группе) | по сообщениям из очереди |
| Независимые читатели | несколько групп consumer'ов на один топик | отдельные очереди / привязки |

### Куда что лучше

**RabbitMQ** удобнее, когда нужна маршрутизация «из коробки», очереди задач,
отложенные или приоритетные сообщения, относительно умеренная нагрузка и короткая
жизнь сообщения.

**Kafka** лучше, когда поток большой, нужно долго хранить события, перечитывать
историю после сбоя или новой версии кода, и когда один и тот же поток читают
разные системы независимо (аналитика, биллинг, уведомления).

Обмен между сервисами — оба варианта; решают нагрузка, нужна ли перечитка истории
и стоимость сопровождения.

«Kafka всегда лучше» — плохой ответ на собесе: смотрят, понимаешь ли ты разницу
между журналом и очередью.

## 14. Spring Kafka: коротко

Не дублируем весь Spring Cloud Stream. На собесе обычно достаточно:

| Режим | Идея |
|-------|------|
| `enable-auto-commit=true` | удобно, ближе к at-most-once риску при падении после commit |
| `ack-mode: record/batch` | контейнер коммитит после успешной обработки record/batch |
| `ack-mode: manual` / `manual_immediate` | `Acknowledgment.acknowledge()` после своей логики → at-least-once |
| `concurrency` | число consumer-потоков ≈ сколько партиций реально утилизируете |

`@KafkaListener` + ручной ack — базовый путь к at-least-once. Exactly-once с БД —
отдельный дизайн (Transactional Outbox, идемпотентный consumer, Kafka transactions).

## 16. Вопросы для собеседования и ответы

### 1. Чем Kafka отличается от «просто очереди»?

Очередь обычно отдаёт сообщение consumer'у и после ack удаляет; конкурирующие воркеры
забирают сообщения из одного потока. Kafka хранит append-only лог с retention, позволяет
replay и независимые consumer group на одних данных. Единица параллелизма внутри группы —
партиция, не отдельное сообщение (в классической модели).

### 2. Как устроено чтение и что будет, если consumers больше partitions?

Consumer с `group.id` входит в группу; координатор назначает партиции. Одна партиция —
один consumer в группе. Лишние consumer'ы idle, пока не освободится партиция или не
увеличится число партиций. Другие группы на том же топике читают полный поток независимо.
Демо: [ConsumerGroupAssignmentDemo.java](code/ConsumerGroupAssignmentDemo.java).

### 3. Зачем offset и можно ли перечитать данные?

Offset — позиция в партиции. Commit фиксирует прогресс группы. После падения новый
member продолжает с committed позиции. Пока сегмент не вычищен retention/compaction,
можно seek/reset и перечитать. Это одно из главных преимуществ log-модели.

### 4. Как гарантировать порядок операций по счёту?

Все события одного `accountId` писать с одним key → одна партиция → один consumer в
группе читает их по порядку. Между счетами (разными партициями) порядка нет. Нельзя
бездумно увеличивать partitions, если держитесь на стабильном key→partition. Нельзя
параллелить обработку записей одной партиции неупорядоченно. Демо:
[KeyBasedPartitioningDemo.java](code/KeyBasedPartitioningDemo.java).

### 5. Когда физически удаляются данные?

При `delete` — целыми сегментами после retention по последнему сообщению сегмента.
При `compact` — cleaner оставляет последние значения ключей, tombstone удаляет ключ.
Точечно «стереть offset 42» штатно нельзя. Демо:
[SegmentRetentionDemo.java](code/SegmentRetentionDemo.java),
[LogCompactionModelDemo.java](code/LogCompactionModelDemo.java).

### 6. Что дают `acks=all` и `min.insync.replicas` вместе?

`acks=all` заставляет leader дождаться ISR. `min.insync.replicas` задаёт минимум таких
реплик; если ISR меньше — запись падает, вместо тихой записи в одного leader'а.
Это сознательный выбор durability over availability.

### 7. Идемпотентный producer — это exactly-once для всей системы?

Нет. Это exactly-once **append в лог Kafka** при retries producer'а (PID + seq).
Consumer с побочным эффектом всё ещё может обработать запись дважды при at-least-once.
End-to-end для пайплайна Kafka→Kafka — транзакции + `read_committed`; для БД — ещё
идемпотентность / outbox. Подробный разбор пути: [§8](#8-семантики-доставки).
Демо: [ProducerRetrySemanticsDemo.java](code/ProducerRetrySemanticsDemo.java).

### 8. At-least-once vs at-most-once на consumer'е?

Весь цикл: `poll` → обработка → `commit` offset группы. Commit **после** успешной
обработки → at-least-once (дубли, если упали после process до commit). Commit **до**
обработки или ранний auto-commit → at-most-once (потеря, если упали после commit).
Producer отдельно может создать дубль в логе при retry без идемпотентности. См. [§8](#8-семантики-доставки).
Демо: [DeliverySemanticsDemo.java](code/DeliverySemanticsDemo.java).

### 9. Чем `commitSync` отличается от `commitAsync`?

Sync ждёт результат и ретраит — проще рассуждать о надёжности, дороже по latency.
Async не блокирует — быстрее, но ошибки нужно обрабатывать самому; на shutdown/rebalance
обычно делают финальный sync.

### 10. Что такое ISR и unclean leader election?

ISR — реплики в синхроне с leader. Unclean election позволяет выбрать лидером отставшую
реплику, если ISR пуст: кластер «оживает», но возможен rollback хвоста лога. На проде
обычно `unclean.leader.election.enable=false`.

### 11. Почему возникает consumer lag и как лечить?

Produce быстрее, чем process; мало партиций; медленные зависимости; частые rebalance;
hot partition. Лечение: профиль обработки, больше партиций/instances (не больше, чем
partitions), вынос тяжёлого I/O, борьба с перекосом ключей. Kafka лаг не «дожимает»
сама — только сигнализирует.

### 12. Чем group coordinator отличается от partition leader?

Partition leader — брокер, обслуживающий чтение/запись конкретной партиции.
Group coordinator — брокер, управляющий membership и offset'ами consumer group.
Это разные роли; один брокер может совмещать их для разных сущностей.

### 13. Когда выбирать Kafka, а когда RabbitMQ?

Kafka — журнал событий: большой поток, долгое хранение, перечитка истории, несколько
независимых читателей одного топика. RabbitMQ — брокер очередей: маршрутизация
«из коробки», очереди задач, быстрое добавление воркеров по сообщениям, короткая жизнь
сообщения. На собесе важно проговорить нагрузку, нужна ли перечитка и как устроена
конкуренция воркеров, а не «Kafka всегда лучше». См. [§13](#13-kafka-vs-rabbitmq).

### 14. Зачем Schema Registry?

Чтобы эволюция бинарного/схемного контракта не ломала consumer'ов молча. Registry хранит
версии схем и проверяет compatibility. Сама Kafka хранит только bytes; смысл полей — на
уровне сериализации и схемы.

### 15. Почему Kafka считается быстрой?

Последовательная запись в лог, сегменты с индексом, опора на page cache ОС, batch на
produce/fetch, параллелизм партициями, pull-модель consumer'а. Брокер хранит и гоняет
**байты**; serialize/deserialize — на Producer/Consumer, не на брокере. Это не «всё всегда
в RAM», а архитектура под последовательный I/O и крупные пачки. См.
[§11](#11-почему-kafka-быстрая).

### 16. Клиент «потерял» кластер, брокеры живы. С чего начать?

С маршрутизации, не с «падения Kafka». Проверить `bootstrap.servers`, сеть и особенно
`advertised.listeners`: в метаданных клиент получает адреса, по которым реально должен
достучаться. Постоянные `NotLeaderForPartition` / коннекты к внутренним хостам —
типичный след неверного advertise или устаревшего кэша метаданных. См.
[§2](#метаданные-и-маршрутизация-клиента).

### 17. Чем JoinGroup/SyncGroup отличается от partition leader? Зачем generation.id?

Partition leader обслуживает чтение/запись партиции. Group coordinator ведёт membership;
в classic protocol group leader (один из consumer'ов) считает assignment через
JoinGroup/SyncGroup. `generation.id` инвалидирует commit'ы member'а прошлого поколения
после rebalance (`ILLEGAL_GENERATION`). См.
[§6](#group-coordinator-joingroup--syncgroup-generation).

### 18. Почему «всё успешно», а latency выросла?

Частый ответ — квоты: брокер троттлит без exception (`ThrottleTimeMs`). Смотреть
`produce-throttle-time-avg` / `fetch-throttle-time-avg`. У async producer при длительном
throttle забивается `buffer.memory` и `send` начинает блокироваться. См.
[§10](#квоты-и-throttling).

### 19. Зачем `group.instance.id`?

Static membership (KIP-345): при кратком рестарте инстанса с тем же ID координатор
не обязан сразу разгонять полный rebalance — ждёт возвращения member'а. Снижает шторм
на rolling deploy. См. [§6](#static-membership-groupinstanceid).
