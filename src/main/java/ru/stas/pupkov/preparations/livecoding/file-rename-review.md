# Code review: переименование файла (БД + filesystem)

## Условие

Веб-система работы с файлами: Java, Spring, React, Postgres. Файлы на диске бэкенда, метаданные в БД. Команда сделала rename — нужно провести code review ключевого метода, найти проблемы и предложить исправления.

```java
@Transactional
public void process(String oldName, String newName) {
    Long id = exec("select id from file where name='" + oldName + "'");
    processFile(oldName, newName); // rename на диске
    exec("update file set name='" + newName + "' where id = " + id);
}
```

## Проблемы (по убыванию важности)

### 1. SQL injection

Запросы собираются конкатенацией строк. `oldName` / `newName` почти наверняка приходят из UI → это пользовательский ввод внутри SQL.

Пример: `oldName = "x' OR '1'='1"` превращает SELECT в условие, которое может вернуть «чужой» id (или сломать парсер). Хуже: `'; DROP TABLE file;--` и подобные payload’ы — в зависимости от того, как устроен `exec` (один statement / несколько, права роли БД).

Даже без классического «дропа таблиц» инъекция даёт:

- чтение/изменение чужих строк;
- обход проверок существования файла;
- при update по сконструированному `id` — порчу метаданных.

**Почему это не «теоретическая дыра»:** имена файлов часто содержат апострофы, пробелы, unicode — даже «честный» пользователь может сломать SQL синтаксически (`O'Brien.pdf`), получив 500 вместо корректной ошибки.

**Фикс:** parameterized query (`PreparedStatement`, `NamedParameterJdbcTemplate`, JPQL/Criteria с параметрами). Имя — только bind-параметр, никогда часть текста SQL. Дополнительно: whitelist символов / нормализация display name, если бизнес это допускает.

---

### 2. Dual-write: `@Transactional` не покрывает диск

`@Transactional` (при типичном `DataSourceTransactionManager` / JPA) управляет **только** транзакцией JDBC/JPA к Postgres: `begin` → commit/rollback connection. Локальный filesystem, `Files.move`, NFS, S3 SDK в эту транзакцию **не входят**. Rollback БД **не** откатит уже выполненный rename на диске.

Исходный порядок операций:

1. SELECT id  
2. `processFile` — диск уже в состоянии `newName`  
3. UPDATE name  

Типичные failure-сценарии:

| Шаг | Что случилось | Итог |
|-----|----------------|------|
| 2 OK, 3 упал (constraint, deadlock, сеть к БД) | tx rollback | На диске `newName`, в БД `oldName` |
| 2 OK, 3 OK, JVM умерла до commit | tx не закоммичена, rollback при reconnect | То же: диск впереди БД |
| 2 упал (файл занят, permission, диск full) | исключение до UPDATE | БД не тронута — ок, но клиенту нужна понятная ошибка |
| 3 OK + commit, а `processFile` был бы *после* commit и упал | — | В БД `newName`, на диске `oldName` — обратный рассинхрон |

Пользователь в UI видит имя из БД, скачивание/превью идёт по пути на диске → 404, отдача чужого файла, «файл пропал», пока кто-то вручную не поправит FS или БД.

**Важный тезис на собесе:** это не баг Spring и не «неправильный `@Transactional`». Это фундаментальный dual-write в два независимых хранилища. Аннотация создаёт **ложную уверенность**, что метод «атомарен».

Связанный эффект: после `processFile` исключение на UPDATE откатит только БД — компенсация FS в коде **отсутствует** (нет `try/catch` с rename обратно).

---

### 3. I/O внутри открытой транзакции

К моменту вызова `processFile` транзакция уже открыта (после SELECT, а иногда и раньше — с входа в метод). Поток держит connection из пула HikariCP/Tomcat JDBC.

Пока идёт rename на диске (особенно сеть/NFS, антивирус, большой directory listing, блокировка файла другим процессом), connection **не возвращается** в пул. При пике параллельных rename:

- пул исчерпывается → остальные запросы к БД ждут / падают по timeout;
- если на строке уже взят lock (`FOR UPDATE` или просто row lock от UPDATE в другом сценарии) — другие сессии стоят, пока FS не закончит.

Правило production-практики: **короткие транзакции, только работа с БД**. Внешний I/O (HTTP, FS, SMTP, брокер) — до tx, после commit, или в отдельном процессе/outbox worker.

Даже если FS быстрый, паттерн плохой: latency диска начинает умножаться на удержание DB-ресурсов.

### 4. Нет валидации и обработки граничных случаев

**Файл не найден.**  
`exec(SELECT…)` может вернуть `null`. Дальше `processFile(oldName, …)` либо падает неочевидно, либо (хуже) UPDATE `where id = null` — в SQL это `id IS NULL` / синтаксис/`0` rows, поведение зависит от `exec`. Клиент должен получить явный 404, а не NPE или «тихий» no-op.

**Конфликт нового имени.**  
Нет проверки `exists(newName)`. Два файла не должны делить одно `name`. Без `UNIQUE(name)` второй UPDATE может перезаписать логику приложения «втихую» или создать дубликаты; с unique — получите `DataIntegrityViolationException` без дружелюбного 409, если не обработать.

**Path traversal и безопасность FS.**  
Если `oldName`/`newName` напрямую склеиваются в путь (`baseDir + "/" + name`), имена вроде `../../etc/passwd` или `subdir/../../../secrets` позволяют читать/писать вне каталога хранилища. Нужны: каноникализация пути, проверка что resolved path лежит внутри base dir, запрет разделителей в display name, либо (лучше) хранение по UUID-ключу вне пользовательского имени.

**Пустые/невалидные имена, регистр, unicode.**  
`""`, `"."`, `".."`, различия `File.PDF` vs `file.pdf` на case-insensitive FS (macOS/Windows) vs case-sensitive Linux в проде — источник «на моей машине работает». Нормализация и единые правила сравнения имён должны быть явными.

**Идемпотентность.**  
Повторный запрос `process(A, B)`, когда уже переименовано в B: должен быть безопасный 404/409/200 idempotent, а не вторая попытка сломать FS.

---

### 5. Гонки (concurrency)

Два запроса одновременно:

**A:** rename `report.pdf` → `a.pdf`  
**B:** rename `report.pdf` → `b.pdf`

Оба делают SELECT, оба находят один id, оба зовут `processFile`, оба делают UPDATE. Последний UPDATE выигрывает в БД; на диске побеждает тот, кто последний сделал `Files.move` — состояние может не совпасть ни с одним из «успешных» ответов клиентам.

Или:

**A:** `x.pdf` → `shared.pdf`  
**B:** `y.pdf` → `shared.pdf`

Без unique + правильной изоляции оба могут решить, что имя свободно (check-then-act), один из rename на диске затрёт/переименует файл другого.

**Что нужно:**

- `UNIQUE` на `name` в Postgres — последний рубеж;
- в транзакции: `SELECT … FOR UPDATE` по строке файла (или optimistic `@Version`) **до** любых побочных эффектов;
- не полагаться на «сначала проверили exists, потом обновили» без блокировки — TOCTOU;
- маппинг unique violation → HTTP 409.

Даже при идеальной БД FS остаётся вне locking-модели Postgres: блокировка строки не блокирует другой ноды/процесса, который пишет в тот же каталог. Отсюда снова аргумент за immutable storage key и rename только метаданных.

### 6. Дополнительные замечания по коду (часто спрашивают)

- **Два round-trip вместо одного.** Можно `UPDATE file SET name = :new WHERE name = :old RETURNING id` (и проверить `rowCount == 1`). Меньше гонок между select и update.
- **Семантика `exec`.** Неясно: prepared или нет, одна колонка, что при 0/N строк, автокоммит. На review это красный флаг API.
- **Нет аудита/логирования.** При рассинхроне БД↔FS без `file_id`, old/new, traceId разбирать инцидент тяжело.
- **Права и multi-tenant.** Нет проверки, что текущий пользователь владеет файлом — IDOR: rename чужого файла, зная имя.

## Как чинить (ответ уровня senior)

1. Параметризованные запросы + `UNIQUE(name)` (+ при необходимости unique по `(tenant_id, name)`).
2. Валидация имён; каноникализация путей; работа по стабильному `id` / storage key, display name — отдельно.
3. **Не** вызывать FS-rename внутри tx:
   - обновить БД в короткой tx, FS — в `TransactionSynchronization.afterCommit` (+ retry / transactional outbox / очередь при сбое диска);
   - либо rename во временный ключ → commit метаданных → финальный move + компенсация;
   - предпочтительно по архитектуре: object storage + immutable object key; «rename» = `UPDATE display_name` без FS.
4. Фоновый reconcile: сверка метаданных БД с фактическим FS/S3, алерт на расхождения.
5. Явные ошибки API: 404 (нет old), 409 (new занят), 400 (невалидное имя).

Полной атомарности БД+локальный FS без распределённых протоколов нет. Цель на проде: сузить окно рассинхрона, сделать операцию идемпотентной и иметь автоматическое восстановление.

## Вопросы для собеседования и ответы

**Почему `@Transactional` здесь почти бесполезен для консистентности?**  
Он гарантирует atomicity только для ресурсов, участвующих в той же транзакции (обычно один DataSource). Локальный filesystem — нет. Rollback БД не откатит `Files.move`. Аннотация лишь создаёт ощущение, что весь метод атомарный.

**afterCommit — это exactly-once rename на диске?**  
Нет. Это только гарантия «FS-операция не стартует, если DB rollback». Если после commit FS упал — снова рассинхрон (БД впереди диска). Нужны идемпотентный retry, outbox и/или reconcile job.

**Почему нельзя просто обернуть FS в «компенсирующий catch»?**  
Можно пытаться: при ошибке UPDATE сделать reverse rename. Но reverse тоже может упасть; при crash между шагами компенсации нет; при параллельных запросах компенсация одного потока ломает другой. Компенсации помогают сузить окно, но не заменяют модель с одним источником истины или outbox.

**Где держать «истинное» имя файла?**  
Частый production-паттерн: на диске/S3 — стабильный ключ (`uuid`), в БД — `display_name` + `storage_key`. Пользовательский rename меняет только строку в БД; FS не трогаем → dual-write исчезает для операции rename.

**Что сказать про SELECT + UPDATE двумя запросами?**  
Между ними гонка. Лучше один атомарный UPDATE по старому имени/`id` с проверкой `rowCount`, плюс unique на новое имя. Блокировка строки (`FOR UPDATE`), если после SELECT ещё есть бизнес-логика до UPDATE.
