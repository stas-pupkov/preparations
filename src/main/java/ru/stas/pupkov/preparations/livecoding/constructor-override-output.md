# Что выведется: `new B()` при вызове `move()` из конструктора `A`

## Условие

Иерархия `B extends A`. В конструкторе `A` вызывается `move()`, в `B` метод переопределён. Вопрос: что напечатает `new B()`?

## Ответ

```
A
1
B
11
```

## Почему так

Порядок при `new B()`:

1. Выделяется объект типа **B**, поля обнуляются → `speed == 0`.
2. Первым отрабатывает конструктор **A** (неявный `super()`):
   - печатает `A`;
   - вызывает `move()`.
3. Диспетчеризация **виртуальная**: даже из конструктора `A` вызывается **`B.move()`**, потому что runtime-тип объекта — `B`.
4. Тело конструктора `B` ещё **не** выполнялось → `speed` всё ещё `0`.
5. `B.move()`: `speed++` → `1`, печать `1`.
6. Далее тело конструктора `B`: `speed = 10`, печать `B`, снова `move()` → `11`.

`hashCode() { return 0; }` в `A` на вывод **не влияет** — отвлекающий фактор.

## Главный takeaway

**Не вызывать overridable-методы из конструктора.** Подкласс ещё не инициализирован (поля, инварианты), а полиморфный вызов уже идёт в него → тонкие баги (NPE, «магические» нули, двойная инициализация).

Безопаснее: `private`/`final` методы в конструкторе, или отложенная инициализация после полной сборки объекта (`static` factory, `@PostConstruct` в Spring — уже после конструктора).

## Вопросы для собеседования и ответы

**Почему вызвался `B.move()`, хотя стек ещё в `A()`?**  
В Java все не-`static`/`private`/`final` методы виртуальные. Выбор реализации — по runtime-типу объекта, не по классу, чей конструктор сейчас выполняется.

**А если бы `speed` объявили и инициализировали полем в `B` (`int speed = 10`)?**  
Поле в `B` **скрыло** бы (`hiding`) поле `A.speed`, а не переопределило. `A` и `B.move()` через `this.speed` могли бы видеть **разные** ячейки — отдельная ловушка. В данной задаче поле одно, в `A`.

**Что будет, если сделать `move()` в `A` как `final`?**  
Компилятор запретит override в `B` (или вызов из `A` всегда шёл бы в `A.move()` при final). Из конструктора `A` печатался бы `0`, затем в `B` — своя логика, если метод назван иначе.
