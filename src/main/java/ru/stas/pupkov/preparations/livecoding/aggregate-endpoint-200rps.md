# Агрегирующий REST endpoint: 3 источника, 200 RPS

## Условие

Бэкенд + UI (Java, Spring, React, Postgres). Спроектировать REST endpoint, который собирает данные из 3 источников и отдаёт в UI, максимизируя throughput и минимизируя latency (компромисс под наши цифры). Пик: **200 RPS**.

| Источник | Норма | Проблема | Можно ли чинить у них |
|----------|-------|----------|------------------------|
| 1 — наш Postgres | ~15 с | очень долгий запрос | да (наш), но в задаче акцент на API |
| 2 — чужой REST | ~5 с | с **100 RPS** деградирует до **~2 мин** | нет |
| 3 — чужой REST | ~10 с | случайные **503** | нет |

## Что прояснить у интервьюера (30–60 сек)

Без этого «правильное» решение плавает:

1. **Данные per-user / per-request или общие?** Если общие или слабо персонализированные — кэш и singleflight дают порядки выигрыша. Если строго per-request с уникальным тяжёлым SQL — 200 RPS × 15 с нереалистичны без смены модели данных.
2. **SLA свежести** — секунды / минуты / «лучше устаревшее, чем 15 с ждать».
3. **Можно ли partial response?** (2 из 3 блоков + placeholder / retry на UI).
4. **Синхронный UX обязателен?** Или допустимы 202 + poll / WebSocket / preloaded dashboard.

Дальше — ответ при разумных допущениях: данные **кэшируемы** (хотя бы на коротком TTL), UI допускает **stale-while-revalidate** и **деградацию** по источнику 3.

## Почему naive-подход не взлетает

### Последовательные вызовы

`15 + 5 + 10 = 30 с` на запрос. Throughput потолкается ещё раньше.

### Параллельный fan-out без кэша

`max(15, 5, 10) = 15 с` — нижняя граница latency на miss.  
При 200 RPS и удержании ~15 с: **concurrency ≈ 200 × 15 = 3000** in-flight только на этот use-case.

Следствия:

- пул коннектов к Postgres на тысячи — неадекватен;
- источник 2 при наших 200 RPS гарантированно уйдёт в режим **2 минуты** (порог 100 RPS);
- источник 3 добавит шум 503 и ретраев → ещё большая нагрузка.

**Вывод:** упираться в origins на каждый UI-запрос нельзя. Цель — **снять 200 RPS с кэша/материализованного среза**, а origins кормить контролируемо и реже.

## Ключевые цифры и компромисс

| Цель | Как достигаем | Цена |
|------|----------------|------|
| Throughput 200 RPS | кэш (local + Redis), coalescing одинаковых ключей | возможна устаревшая выдача |
| Latency ≪ 15 с на hot path | cache hit / precompute | freshness SLA |
| Не уронить источник 2 | bulkhead + rate limit **&lt; 100 RPS** (лучше 50–80 с запасом) | очередь обновлений, stale при пике |
| Жить с 503 источника 3 | timeout, retry с jitter (1–2 раза), circuit breaker, partial UI | иногда блок 3 пустой/старый |

Серебряной пули нет: **либо свежие 15 с и низкий RPS, либо высокий RPS и управляемая устарелость**. Под пик 200 RPS выбираем второе.

## Целевая архитектура (как рассказывать на собесе)

```
UI ──200 RPS──► BFF/API
                  │
                  ├─► Cache (Caffeine → Redis) ── hit? return aggregate
                  │
                  └─ miss / soft-expire ──► Aggregator (async refresh)
                         │
                         ├──► DB      (свой пул, тяжёлый запрос → лучше async job / matview)
                         ├──► S2      (Semaphore/RateLimiter ≪ 100 RPS, отдельный bulkhead)
                         └──► S3      (timeout ~12–15 с, retry 503, CB, fallback)
```

### 1. Параллелизм на miss

`CompletableFuture` / WebClient + `Zip` / Resilience4j: три вызова **параллельно**, итог = `max` латентностей при успехе, а не сумма. На sync-пути без кэша всё равно ~15 с из‑за БД — поэтому miss должен быть **редким**.

### 2. Кэш и singleflight

- Ключ: userId / dashboardId / «global» — по модели данных.
- TTL + soft-TTL (stale-while-revalidate): отдать stale сразу, в фоне один refresh.
- **Singleflight / request coalescing:** 50 одновременных miss по одному ключу → **один** fan-out к origins, остальные ждут тот же Future. Критично, чтобы не умножить RPS на источники.

### 3. Источник 2: жёсткий bulkhead

Их деградация на 100 RPS — жёсткое ограничение нашей исходящей нагрузки:

- `RateLimiter` / очередь обновлений: исходящий RPS к S2, например, **≤ 60–80**;
- отдельный пул потоков / connection pool только для S2 (ошибка S2 не забивает DB-пул);
- при отказе лимитера — отдать stale из кэша или placeholder, **не** ждать 2 минуты;
- timeout на S2 в нормальном режиме ~5–7 с; если пошло > порога — считать деградацией и резать.

Иначе один «успешный» шторм с UI убивает S2 для всех.

### 4. Источник 3: устойчивость к 503

- Retry только на 503/408 (идемпотентный GET), **с jitter**, бюджет 1–2 попытки.
- Circuit breaker: при всплеске 503 быстро открывать → fallback (stale / empty section), чтобы не долбить их ретраями.
- UI: блок виджета 3 в состоянии «временно недоступно», остальное показать.

### 5. Postgres 15 с

Даже «наш» источник — главный якорь latency. На собесе обязательно предложить (по возможности):

- не гонять 15-секундный SQL на request path: **материализованное представление / таблица-срез**, обновляемая job’ом;
- читать из read-replica / Redis, прогретых прогревом;
- если SQL неизбежен — сильно меньше RPS к БД за счёт кэша и coalescing (например, единицы–десятки refresh/sec, не 200).

Иначе математика concurrency убивает пул.

### 6. Контракт API с UI

Варианты (выбрать по SLA):

- **200 + полный JSON** из кэша (основной happy path);
- **200 + partial** (`source3: null`, `degraded: true`) при CB/timeout;
- тяжёлый cold start: **202 Accepted** + `Location` на результат / websocket — если 15 с sync неприемлемы для React.

Не отдавать UI зависание на 2 минуты из‑за S2.

### 7. Наблюдаемость

Метрики per-source: latency, error rate, bulkhead rejections, cache hit ratio, in-flight. Алерт: «S2 latency > 10 с» или «исходящий RPS к S2 → 90». Без этого деградация S2 заметится по жалобе пользователей.

## Чего не делать

- Синхронно звать все три origins на каждый из 200 RPS.
- Общий пул потоков без изоляции (S2/S3 забьют всё).
- Бесконечные ретраи на 503 источника 3.
- Держать HTTP-запрос UI открытым, пока S2 отвечает 2 минуты.
- Игнорировать, что 15 с × 200 RPS ≈ 3000 concurrent к БД.

## Вопросы для собеседования и ответы

**Почему нельзя просто «сделать всё async через @Async»?**  
Async не уменьшает работу origins и не лечит лимит 100 RPS у S2. Без кэша/лимитов/bulkhead вы лишь перемещаете 3000 задач в другой пул.

**Как выбрать лимит на S2?**  
Их порог деградации — 100 RPS. Ставим исходящий лимит с запасом (например 50–80), плюс мониторинг latency. Цель — никогда не быть причиной их 2-минутного режима.

**Что важнее на пике: свежесть или latency?**  
При 200 RPS и 15 с БД — latency/availability. Свежесть обеспечивается фоновым refresh в пределах rate limit, а не синхронным hit origins.

**Можно ли обойтись без Redis?**  
Local Caffeine хватит на один инстанс и общие ключи; при нескольких нодах BFF без общего кэша каждая нода бьёт origins → легко суммарно превысить 100 RPS на S2. Для 200 RPS на кластере почти обязателен shared cache или центральный refresher.
