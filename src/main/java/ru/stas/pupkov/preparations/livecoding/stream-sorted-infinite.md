# Какой результат: `iterate` + `sorted` + `limit`?

## Условие

```java
IntStream.iterate(1, x -> x + 1)
    .sorted()
    .limit(5)
    .forEach(System.out::print);
```

## Ответ

**Зависание** (практически бесконечное выполнение / в итоге `OutOfMemoryError` при росте буфера). До `forEach` выполнение не доходит — **ничего не печатается**.

Не `12345` и не исключение сразу при старте.

## Почему

1. `iterate(1, x -> x + 1)` — **бесконечный** упорядоченный стрим: 1, 2, 3, …
2. `sorted()` — stateful intermediate: чтобы отсортировать, нужно **увидеть все элементы** (буферизация).
3. На бесконечном источнике `sorted()` никогда не завершит накопление → `limit(5)` **не успевает** обрезать поток «снаружи» так, чтобы спасти ситуацию: short-circuit после `sorted` не отменяет необходимость полного входа в sort.

Порядок intermediate важен:

```java
// OK → 12345
IntStream.iterate(1, x -> x + 1).limit(5).sorted().forEach(System.out::print);
```

Сначала конечный префикс, потом sort.

## Вопросы для собеседования и ответы

**Почему `limit` «справа» от `sorted` не помогает?**  
Потому что pipeline тянет данные слева направо по запросу терминальной операции, но `sorted` обязан потребить весь upstream, прежде чем отдать хоть один элемент downstream. `limit` ждёт элементы от `sorted`, а `sorted` ждёт конец бесконечного `iterate`.

**`distinct` на бесконечном `iterate`?**  
Аналогично может не завершиться, если уникальных значений бесконечно много (как здесь). На конечном множестве значений (например `iterate(0, x -> (x+1)%3)`) — другая история.

**Где ещё такая ловушка?**  
Любая операция, требующая полного материалала стрима (`sorted`, некоторые формы `collect` без short-circuit), на заведомо бесконечном источнике без предварительного `limit`/`takeWhile`.
