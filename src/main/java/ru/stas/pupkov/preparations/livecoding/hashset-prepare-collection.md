# Какое число вернёт `prepareCollection()`?

## Условие

```java
public static int prepareCollection() {
    Set<A> set = new HashSet<>();
    set.add(new A());
    set.add(new B());
    set.add(new B());
    return set.size();
}
```

Допущение: у `A` / `B` **дефолтные** корректные `equals` / `hashCode` из `Object` (равенство по ссылке, hash от identity). Для компиляции `B` должен быть совместим с `A` (обычно `B extends A` или `A` — интерфейс и `B implements A`).

## Ответ

**3** (если код компилируется при допущениях выше).

Если `A` и `B` **не связаны** по типу — `set.add(new B())` не компилируется, до `size` выполнение не доходит.

## Почему

Три вызова `new` → три разных объекта в куче.  
`Object.equals` сравнивает ссылки → ни одна пара не равна → `HashSet` принимает все три добавления → `size == 3`.

Связь `B <: A` нужна только для типов; на размер при default-equals она не влияет — важен identity, не runtime-класс.

## Вопросы для собеседования и ответы

**Почему два `new B()` не схлопываются в один элемент?**  
Потому что это разные экземпляры. Default-equals не смотрит на класс и поля — только на `==`.

**Когда был бы другой ответ?**  
Только если переопределить `equals`/`hashCode` (например, равенство по полям или «все экземпляры класса равны»). В этой формулировке — не наш случай.

**А если не сказано, что `B extends A`?**  
Тогда либо подразумевают совместимость типов (иначе зачем `Set<A>`), либо код не компилируется. Без subtype-связи у `add(new B())` — ошибка компиляции, не число.
